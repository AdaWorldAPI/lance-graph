## CP-3: TEST REQUIRED. wasm `mul_add` and `reduce_sum` are separate facts

Two independent observations in ndarray, neither explaining the other:

1. **`mul_add`.** `src/simd_wasm.rs` now rounds once by design. f32 is
   computed in f64 with round-to-odd addition (`fma_f32_in_f64`, `:2461`); f64
   uses an emulated Boldo–Melquiond FMA inside a checked operand range with a
   lane fallback (`:551-563`). `crates/simd-masking-parity`
   `check_mul_add_single_rounding` compares against an exact oracle with
   double-rounding tie fixtures. `simd-matrix.yaml:380-383` runs it for wasm
   with and without `simd128`. That is sampled evidence (the f32 arm runs 4096
   rounds of 16 lanes; the f64 arm's fixture count was not read), not a proof. ndarray's own `.claude/blackboard.md` (2026-10-11,
   "Open: `mul_add` not bit-identical across realizations (wasm)") and
   `knowledge/wasm-simd-consumer-guide.md` (table row "`mul_add`: two
   roundings") were never reconciled with the change. The guide's row is now
   stale for the default build. The `relaxed-simd` caveat (`simd_wasm.rs:37-38`)
   is a separate leg that the parity run does not cover.
2. **`reduce_sum`.** wasm uses a balanced tree, the scalar backend a
   sequential fold (consumer guide table). That is an ordering difference in a
   different operation. It does not bear on `mul_add` and does not retire the
   warning.

**Required:** a parity result that names realization, target features and
fixture set for `mul_add` (with `relaxed-simd` stated as in or out of scope),
and a separate statement of the `reduce_sum` tolerance contract. Both are
ndarray-side edits, out of scope for this lance-graph PR.
