## Gaps, in one list

1. **No TFLite integer nonlinearity exists natively.** ndarray has the requantize
   primitives (`simd_fixedpoint.rs`, #375) but no gemmlowp `exp_on_negative_values`,
   `tanh`, `logistic` or `one_over_one_plus_x_for_x_in_0_1`, and no 256-entry code table.
   D-TFLP-1 is genuinely unbuilt.
2. **No independent TFLM oracle is in any tree.** The #375 tests check `requantize_i32_to_i8`
   against `reference_epilogue`, which is built from the same scalar family; the only TFLM
   golden is `quantize_multiplier(3.7) == (1_986_422_374, 2)`. Bit-exactness with TFLM is
   CLAIMED in the module doc, not tested.
3. ⊘ **Struck by Amendment 1 §A4 — the capstone was right.** The TFLite int8 spec requires
   weight zero point 0 for per-tensor and per-axis weights alike, and TFLM's own FC prepare
   asserts it (`fully_connected_common.cc:147`, a `DCHECK`). The kernel capability below is
   an extension outside the conforming profile. Original text: *The capstone's "weights zero
   point 0" is per-channel only.* TFLM per-tensor FC has
   `filter_offset = params.weights_offset` (`fully_connected.h:145`) and
   `acc += (filter_val + filter_offset) * (input_val + input_offset)` (`:167`). The
   `filter_offset·Σa` term depends on the activation and cannot be folded into the bias.
4. **int8 TANH/LOGISTIC in TFLM are fixed-point, not a lookup.** `integer_ops/tanh.h:28-60`,
   `logistic.h:27-57`. The 256-entry `LUTPopulateInt8` table is a desktop-TFLite design;
   in Micro only `softmax_common.cc` calls `LUTPopulate`, and only for int16. A 256-entry
   table is still exact *if it is generated by running the fixed-point kernel over all 256
   codes*; it is not exact if generated by `LUTPopulateInt8`'s float `round(f(x)/s)+z`.
5. **int8 TANH is asymmetric.** It saturates to −128 and 127 (`tanh.h`), so tanh(−x) ≠
   −tanh(x) in code space. No odd-mirror half table.
6. **Rounding mode is not a property of "int8".** TFLite `TfLiteRound` is ties-away
   (`cppmath.h:36`); ONNX `QuantizeLinear` is ties-even. A shared quantize helper must
   take the mode as a parameter.
7. **R2IL refuses value Select.** `FoldDialect` refuses `BLEND` (`r2il/src/lib.rs:38`),
   although mask-risc has the terminal (`mask-risc/src/ir.rs` `BlendI32`). The
   Greater→Where→Sum chain reaches R2IL only as the fused masked sum.
8. **Overflow semantics differ per arm.** `masked_sum_i32` widens to i64; ONNX
   `sum_where_greater_i32` refuses results outside i32 (`OutOfDtypeRange`). `gemm_u8_i8` /
   `matmul_i8_to_i32` accumulate in i32 on every arm (`vpdpbusd`, never `vpdpbusds`;
   AMX `tdpbusd`; WASM `extmul`+`extadd`), which wraps; TFLM's C++ `int32 +=` overflow is
   UB. They agree only on inputs whose accumulator stays in range — a precondition, not a
   guarantee.
9. **A documentation overclaim in lance-graph-onnx.** `lib.rs:73-74` says the bounds "are
   gated in ndarray's own tests (≤ 2 ULP)". For `vsexp`, ndarray's test gates relative error
   `< 4e-6` (`vml.rs:1535`), about 34 ULP. Only `vstanh` carries a 2-ULP doc bound
   (`vml.rs:646`). The 1-ULP figures are lance-graph-onnx's own sampled measurements.

## C. Polyfill reuse map

- **Missing primitives:** gemmlowp `exp_on_negative_values`, `tanh`, `logistic`,
  `one_over_one_plus_x_for_x_in_0_1` (TFLM `fixedpoint.h:711-863`). Natural home: beside
  `simd_fixedpoint.rs`. Scalar is enough; they run once per table entry, never per element.
- **Missing code-domain tables:** 256-entry int8 TANH/LOGISTIC, the softmax exp-of-diff table.
  Key = (input scale, input zp, output scale, output zp, function).
- **Present, needs binding only:** `gt_i32_to_mask`, `blend_i32`, `masked_sum_i32`,
  `multiply_by_quantized_multiplier*`, `requantize_i32_to_i8`, `gemm_u8_i8`,
  `matmul_i8_to_i32` (already implements the capstone's u8 shift trick, `amx_matmul.rs:960-966`
  + `subtract_i8_to_u8_bias` at `:1019`).
- **Present in mask-risc, unwired in R2IL:** `BlendI32`, `ScatterCountU32`.
- **Missing oracles:** compiled TFLM reference kernels for TANH, LOGISTIC, ADD, MUL, SOFTMAX,
  FC. This is the gap that gates every EXACT-CANDIDATE above.

## D. Cross-dialect equivalence fixture — `Σ select(X > t, X, 0)`

Input `X: [i32; n]`, scalar `t`.

| arm | expression | result type |
|---|---|---|
| ONNX | `Greater(X,t) → Where(m,X,0) → ReduceSum` = `sum_where_greater_i32` | i32 or `OutOfDtypeRange` |
| TFLite | `GREATER → SELECT_V2 → SUM` (reading only; no facade exists) | i32, overflow behaviour unread |
| native direct | `gt_i32_to_mask` + `masked_sum_i32` | i64 |
| R2IL | `and_cmp_i32(Gt)` pushes `t` then the lane, `IntSLess` (`procs.rs:257-284`), then `SUM` | i64 |
| RelAlg | `Rel::Atom(I32{op:Gt})` + `Measure::Sum` → `Answer::Sum(i64)` | i64 |
| scalar oracle | `x.iter().filter(|&&v| v > t).map(|&v| v as i64).sum()` | i64 |

Cases: random in-range; `t = i32::MAX` (empty, sum 0); `t = i32::MIN` (all but MIN);
all-`i32::MAX` with n = 2 — the i64 arms agree, ONNX must refuse. **Counterexamples**
(must disagree, and the test asserts that they do): the overflow case above; R2IL with an
explicit `BLEND` (must return `FoldError::Unimplemented`, not a value); a nullable lane
under `Rel` (K3 drops NULL rows, ONNX has no NULL). Do not assert universal equality.

1. **TFLite int byte-exact natively?** Not yet for any nonlinearity (missing); requantize is a
   candidate with no oracle. Integer compare/select/sum: yes, within range.
2. **ONNX same method?** For integer compare/select/sum, yes, with an i32-fit refusal. For

   (scales, zero points, rounding mode, function) and the hot path stays in code space.
6. **Which parity?** Today: native-executable parity across SIMD arms, BOUNDED parity to ONNX

### A3. Compile-time vs load-time table preparation

Two separate decisions, which the capstone conflates:

1. **Codec policy** (storage, code space, rounding, NaN policy) is compile-time in both plans.
   A prepared table read by a monomorphised lookup involves no runtime policy dispatch. No
   conflict here.
2. **Table content and calibration** is where they differ. Codec8 production calibrations are
   marker types generated from a calibration manifest (plan D8); "runtime calibration in
   production" is listed as superseded (plan §9). Capstone §4 builds every table "at load"
   from the model file.

What the source settles:

- The TFLM int8 TANH output for a code is a function of the **input** calibration only:
  prepare reads `input->params.scale` into `input_multiplier`, `input_left_shift` and
  `input_range_radius` (`tanh.cc:61-72`), eval subtracts the input zero point, and the output
  arithmetic is fixed at Q0.7 (`integer_ops/tanh.h`, `kOutputScale = 7`). LOGISTIC is the same
  with a fixed output zero point of −128 (`logistic_common.cc:46-62`). So each table is a pure
  function of one `Calibration` marker.
- Therefore, **for models that are build inputs**, a TFLM table fits D7/D8 unchanged: the
  manifest supplies `SCALE`/`ZERO_POINT`, the generator writes a const table. No new seam.
- **For models that arrive at run time**, the only route the ratified plan allows is
  `lab-calibration` (owned `Box<[T::Elem; 256]>`, fallible `prepare()`, `&self` lookup, off by
  default) — which is lab-only and unbuilt.

**Missing seam (OPEN, operator decision):** production preparation of tables for models not
known at build time. Options, none chosen: (i) models are build inputs only (per-model
generation); (ii) a production owned-table route modelled on `LabCodec8` — runtime *data*
under compile-time *policy* — which reverses the §9 supersession and needs a ruling;
(iii) load-time preparation stays in the lab. Capstone §4 should say it depends on this
decision rather than assume load time.

**Domain A vs Domain B on the shared table shape.** Codec8 D7 defines a table cell as the
correctly rounded tanh of the exact decoded f32 value, certified against mpmath (G7). That is
a mathematical contract. The TFLM TANH table cell is whatever `integer_ops/tanh.h` outputs.
The two may share storage (`[i8; 256]`), index convention and generator plumbing, but they are
different source identities with different certification: G7 does not certify a TFLM table,
and a TFLM golden-vector gate does not certify a D7 table. Plan §3's finding that TiesEven and
TiesAway give identical tanh tables concerns the mathematical table only.

**Ownership conflict to flag:** Codec8 plan §7 lists "A port of TFLM's gemmlowp code (facade
work, later)" as a non-goal, while §2 says facades only re-export. The fixed-point
`tanh`/`logistic`/`exp_on_negative_values` therefore has no owner today. By the re-export
ruling it belongs in ndarray beside `simd_fixedpoint.rs`; the Codec8 plan would need one line
changed to say so.

### A4. FC weight zero point (corrects gap 3)

- **Conforming int8 FC:** weight zero point 0, per-tensor and per-axis alike (TFLite int8
  quantization spec; TFLM asserts it in prepare, `fully_connected_common.cc:143-147`, as a
  `DCHECK`, so only in debug builds). The capstone's bias fold (§3.4) is an exact
  mathematical identity here. Byte identity still depends on accumulator range, rounding and
  requantisation, which stay EXACT-CANDIDATE until an oracle runs.
- **`weights_offset ≠ 0`:** the generic reference kernel accepts it (`fully_connected.h:145,167`)
  and it adds `weights_offset·Σa`, which no bias can absorb. Classify as outside the admitted
  profile: REFUSE at admission. Build no row-sum for it.
- Kept: accumulator overflow gates, per-channel multiplier/shift tests, reduction lengths that
  are not multiples of 16/64, and the per-arm instruction check (all arms `vpdpbusd` / AMX
  `tdpbusd`, non-saturating; shift and bias correction already in `matmul_i8_to_i32`,
  `amx_matmul.rs:960-966,1019`).

### A5. Output quantization as admission constraints

Spec profile for int8: TANH 1/128 and 0; LOGISTIC 1/256 and −128; SOFTMAX 1/256 and −128.
TFLM Micro enforces less than the spec:

| op | TFLM int8 prepare checks | source |
|---|---|---|
| TANH | none on the output | `tanh.cc:61-72` (the zp/scale checks at `:87-88,123` are the int16 branch) |
| LOGISTIC | output zero point = −128; scale not checked | `logistic_common.cc:46-47` |
| SOFTMAX | output zero point = −128 and scale = 1/256 | `softmax_common.cc:103-104` |

The output arithmetic is fixed inside the kernels, so a model declaring another output scale
gets TFLM bytes under a wrong label. Our admission checks the spec, which makes it stricter
than TFLM for TANH and LOGISTIC; the negative admission tests are exactly those cases.

D-TFLP-1 fixtures vary the **input** calibration (scale, zero point; small and large scales,
zero points near both ends, codes beyond `input_range_radius`) and keep the operator's output
quantization fixed. They are fixtures, not codec modes. The existing Codec8 tests for
`Asym`/`Sym`/`NaNAtMin`/`UnitFull` and the three roundings stay as they are. `TfliteAct`'s
`TiesAway` covers only the quantize step; the kernel's intermediate rounding
(`SaturatingRoundingDoublingHighMul`, `RoundingDivideByPOT`) and saturation are separate and
must match on their own.

4. **ONNX**: output equals an ONNX Runtime fixture for a stated opset and domain.
5. **Cross-dialect**: two external readings normalise to one admitted native method under
   identical guards.

## Amendment 2 (2026-10-26) — canonical operators and native ClassId aliases

### B1. Two syntax domains, one execution substrate

| | canonical (ONNX, TFLite) | native (ours) |
|---|---|---|
| recognised by | the canonical format | our ClassId metadata envelope |
| identifier | (domain, operator, version) | (ClassId, alias) |
| authority | the upstream spec | our recipe definition |
| may lower to | an existing native LUT or polyfill, **after** certification | the same, by explicit alias |
| identity after lowering | unchanged: still the canonical operator | unchanged: still the alias |

Four identities stay separate and are all recorded: canonical identifier, native identifier,
implementation (native method or polyfill), and prepared data (model parameters, calibration,
LUT revision, codebook generation). The prepared-data half is the D-NAM-PZL "recipe receipt"
(`d-nam-palette-native-lut-capstone-v1.md:40`); no new identity scheme is needed. Two names may
resolve to one implementation only where both contracts permit it. There is no shared
operator registry and no runtime dialect switch: resolution happens before execution and the
compiled recipe is frozen.

### B2. Worked example: canonical Mish vs a native Mish alias

- **Canonical.** ONNX defines `Mish` (opset 18, floating-point types only), which
  `lance-graph-onnx` does not admit today; an f32 reading would be BOUNDED, like Tanh. TFLite
  has no Mish builtin; a converted model carries it as a chain (`x · tanh(softplus(x))`) or as
  a custom op. A custom op with an unverified
  implementation and version is REFUSE. A chain is certified op by op, including each
  intermediate quantization: composing 256-entry code→code tables reproduces intermediate
  requantization by construction, and the multiply is a function of one input code, so a
  fused table is exact **if every op in the chain is itself reproduced exactly**.
- **Finding against capstone §3.1.** In TFLite Micro the chain cannot be all-int8: `EXP` is
  float32 only (`exp.cc:41`) and `LOG` is float32 only (`elementwise.cc:46-47,390-392`). A
  converted int8 model therefore carries dequantize/float/quantize islands, and their output
  depends on the platform `expf`/`logf`, which no TFLM commit pins. "Exact against running the
  chain op by op in TFLM" holds only with a pinned libm, or as BOUNDED otherwise. Full TFLite
  may differ (its kernels were not read): OPEN.
- **Native.** A ClassId alias such as `mish2lut` names our own recipe: a 256-entry table under a
  stated Codec8 policy (for example `Asym` input, a named output space and rounding), built
  from the mathematical function. Its contract is ours. It is a calibrated or mathematically
  certified native approximation, never "TFLite Mish", and it cannot be exported under a
  canonical name.
- **If certification fails** for the canonical chain, the LUT is not substituted under the
  canonical name; the chain runs through its admitted per-op implementations or is refused.

Certification of a canonical reading is conditional on operator version, dtype, shape, layout,
code space, arithmetic, rounding, NaN behaviour, saturation and output representation (§A5),
and lands in one of four classes: exact equivalence, bounded compatibility, calibrated native
approximation, or unsupported. A proof for one operator version or one alias certifies no
other reading.

### B3. Codec8 under both domains

Both domains reuse `Codec8<T, S, R, N>` and `Calibration` (§A1-A2) unchanged; data
representation and operator execution stay separate contracts. Because `Asym` and `Sym` share
`Elem = i8` (§A2), an alias that consumes a canonical tensor must take the code space from the
canonical operator's quantization, never from the byte buffer: a TFLite activation code −128 is
a value and must never reach a `Sym + NaNAtMin` table as NaN.

- STORAGE-READING resolution per concept.

### C3. Recommendation: keep the systems separate; reuse the discipline, not the types

**1. What it provides.** See C2.

**2. Can it be reused without `ogar-vocab`?** The socket is zero-dep. Its semantics are not.
- `HotPlug.classids` are OGAR-minted concept ids. `covered` names OGAR capability tables.
- Using it for native method binding would need a minted classid per operator, model or LUT recipe. That is out of scope here, and minting is forbidden in lance-graph.
- It would also make canonical ONNX/TFLite admission depend on an ontology authority.
- So: no type reuse.

**3. Who owns what (facts).**

| system | role |
|---|---|
| Quack | resolve-once membrane: query names and literals → numeric `Query` (`bind.rs`: `Binder`). Lowers to a mask-risc Program and never evaluates. Deps are only `lance-graph-mask-risc` and `lance-graph-contract`; "No ndarray dep". |
| `Registrar` (Quack trait) | names a table-catalog seam. It has NO production implementation (`bind.rs:405`). |
| R2IL | the fold dialect, with named refusals |
| mask-risc | the single executor and terminals over masks |
| ndarray | kernels, Codec8 policies, fixed-point requantize, GEMM, and now the TFLM oracle fixture |

Numeric operator binding (LUT, GEMM, requantize) is not a masking operation. Today it has no home in Quack.

**4. OGAR activation: optional semantic enrichment only.**
- The one legitimate overlap is a NATIVE model (Amendment 2's ClassId domain) that already carries an OGAR concept.
- Activating that concept through HotPlug could attach vocabulary or a storage reading.
- It is never on the canonical ONNX/TFLite path.
- It is not needed to bind or execute a numeric recipe.

**5. How to avoid duplication.**
- (a) Do not add a second capability registry. Capability names stay in OGAR tables. A model-binding profile is not a capability.
- (b) The profile's identity already exists: the D-NAM-PZL recipe receipt. It carries model/layer/weight identity, the codebook+calibration digest, the exact-vs-bounded declaration, and the LUT table identity. Key profiles by that, not by ClassId.
- (c) Dispatch stays compile-time Codec8 policy plus prepared data. No runtime polyfill dispatch table is needed.
- (d) Copy the shape `bind.rs` already says it follows: "the same lifecycle as hotplug's SlabDeclaration → resolve_for_context → ResolvedReading". That means:
  - a zero-dep trait for an external owner;
  - resolve once at a boundary;
  - a typed drift enum;
  - fail closed;
  - no `Default`.
- An ICC-like profile store is then a second seam beside `Registrar`, with no owner yet. Name it. Do not build it. Its owner is the same open decision as Amendment 1 §A3 (build-time vs load-time preparation).

**Verdict.** Keep the systems separate. Extract no abstraction now: there is one candidate user and its owner is undecided.

## Amendment 4 (2026-10-26) — which parts of the Fisher-z / softmax roundtrip never needed to exist

Read: `crates/bgz-tensor/src/fisher_z.rs` (FamilyGamma, FisherZTable, lines 1-225), ndarray
`src/hpc/codec8.rs` and `.claude/knowledge/coresearch-2026-10-24-i8-codec8-map.md` (X20, X25-X28),
`d-nam-palette-native-lut-capstone-v1.md` (§58 softmax, §60 closure gate, F6), ndarray
`hpc/activations.rs` `softmax_f32`, TFLM `reference/softmax.h:70-140` and `softmax_common.cc:100-135`.
Probe: `.claude/probes/fisherz-softmax-v1/` (script, TFLM harness, results). Production code unchanged.

### E1. The contract being substituted

`FamilyGamma` (fisher_z.rs:63-76): encode `trunc(clamp((atanh(clamp(c, ±0.9999)) − z_min)/z_range · 254 − 127, −128, 127))`
(`as i8` truncates toward zero; it does not round); decode `z(q) = z_min + (q + 127)/254 · z_range`,
then `tanh`. `z_range ≥ 1e-10 > 0` by construction (`:57`). So the codes are an affine int8 quantization
of z with scale `s = z_range/254` and a real, generally non-integer, zero point `−127 − 254·z_min/z_range`.
Exactness below is always about the decoded **representatives** `z(q)`; the original values were lost at
encode (E4.6).

### E2. Derivation, with every cancelled term

1. `z = atanh c` ⇒ `e^{2z} = (1+c)/(1−c)` ⇒ `e^{βz} = ((1+c)/(1−c))^{β/2}`, so
   `p_i = ((1+c_i)/(1−c_i))^{β/2} / Σ_j ((1+c_j)/(1−c_j))^{β/2}`. At β = 2 the weights are the rational
   odds `(1+c)/(1−c)`: no transcendental function remains when starting from cosines. (Not our case:
   the stored quantity is q, not c.)
2. Binary: `p_1 = σ(β(z_1 − z_2))` and `2σ(x) − 1 = tanh(x/2)`, so `atanh(2p_1 − 1) = β(z_1 − z_2)/2`.
   The output map is `atanh(2p − 1)` (half the logit of p) — not a FamilyGamma Fisher-z of a probability.
3. Substitute E1: `z(q_1) − z(q_2) = (z_range/254)(q_1 − q_2)`. `z_min` cancels, `+127` cancels, so
   **`atanh(2p_1 − 1) = β·z_range·(q_1 − q_2)/508`**.
   Cancelled from the runtime path: decode, tanh, exp, the normalization, atanh. What remains is one
   integer subtraction; the factor `β·z_range/508` is a per-family constant, and a consumer that accepts
   `q_1 − q_2` as the statistic needs not even that.
4. N-way: `p_i = e^{k(q_i − q_max)} / Σ_j e^{k(q_j − q_max)}`, **`k = β·z_range/254`**. Since k > 0, the
   maximum is the maximum code; `d_i = q_i − q_max ∈ [−255, 0]`.

Conditions under which (3) and (4) hold exactly over the reals: one FamilyGamma for every element; the
softmax is over `β·z` (path A below), not over `cos = tanh z`; `q = −128` included (decode is the affine
continuation, finite); p is never 0 or 1 for real arithmetic because `|Δq| ≤ 255`.

### E3. What is static and what is dynamic (path A)

| part | when | cost |
|---|---|---|
| `L[d] = round(2^F·e^{k d})`, d ∈ [−255, 0] | preparation, per (β, z_range); **independent of z_min** | 256 entries: 1 KiB (u32) or 2 KiB (u64) |
| max over codes | run time | one i8 horizontal max |
| `d_i = q_i − q_max` | run time | one subtract per element (fits i16; `q_max − q_i` fits u8) |
| `w_i = L[d_i]` | run time | one gather per element (256 × u32 is too wide for a single byte permute) |
| `S = Σ w_i` | run time | integer adds; `S ≤ N·2^F` |
| normalization | run time, once per row | one reciprocal or division per row; per element only if p itself is the output |

- **Fused consumers:** `y = Σ_i w_i V_i / S` divides once per output component, so p is never materialized.
- **Ranking and argmax** need no exponential at all: the order of codes is the order of p.
- **Histogram form:** `S = Σ_c h[c]·L[c − q_max]` is the same integer and was asserted equal on every case.
  Whether it is faster than direct gathers is unmeasured.
- **Masking:** a masked element is excluded from both the max and the sum.
- **Temperature change:** a new β means a new L, i.e. 256 exponentials at preparation time.

**The existing TFLM int8 softmax already is this algorithm.** `softmax.h` computes
`input_diff = input − max_in_row`, folds `β·input_scale` into one multiplier (`softmax_common.cc:123-126`),
never reads the input zero point, accumulates in Q12, and takes one reciprocal per row. Fed FamilyGamma
codes with `input_scale = f32(z_range/254)`, it computes FisherZ softmax directly, and the non-integer zero
point is irrelevant.

### E4. Where it stops being true (counterexamples, measured unless marked derived)

1. **Mixed calibrations in one row.** `z_min` and `z_range` no longer cancel. A 5-element vector under G1
   and G3 gave a code-formula error of 0.48 in p and the wrong argmax (reference index 3, code index 0).
2. **Path B, softmax over `cos = tanh z`.** The weight depends on both codes, not on their difference: at
   d = −10 under G2 the weights are 0.991 (codes 117, 127) and 0.920 (codes −110, −100). It stays in code
   space only as a pair table `L2[q_i][q_max]` (65,536 entries per (β, gamma)), still followed by an
   integer sum and one normalization.
3. **Path C, a native Palette256 whose codes are indices, not an affine axis** (derived, not probed). No
   difference structure exists, and the code maximum is not the value maximum unless the palette is
   ordered. It needs a representative-indexed pair table, as in path B.
4. **Path D, `Palette256:Palette256` laws** (derived). A `FisherZTable[a][b]` lookup returns FamilyGamma
   codes under one gamma, so path A applies to its output. The softmax output, however, is a probability,
   not a FisherZ code. Feeding it into another palette law is a re-encode under the closure gate
   (capstone §60, EXO-129/132), so the chain is not closed.
5. **The f32 roundtrip is worse than redundant.**
   - Binary, exhaustive over 65,536 pairs: the f32 chain `decode → softmax → atanh(2p−1)` is non-finite
     on up to 58,564 pairs (G3, β = 32), 13,954 for G1 at β = 32, and 45 for G2 already at β = 8.
   - A 50-digit evaluation of the explicit chain also overflows for G3 at β = 32.
   - The closed form is finite for every pair; its f64 evaluation agrees with the 50-digit chain to ≤ 7e-15
     wherever the chain is finite.
6. **FamilyGamma's own codec is not a fixed point** (a finding about an existing contract; not changed
   here, since FamilyGamma is a declared non-consumer of Codec8).
   - `encode(decode(q)) ≠ q` for 59-77 of 256 codes per gamma, because `as i8` truncates toward zero
     after f32 rounding.
   - −128 is reachable only for inputs below the family and decodes to a finite cosine (G2: −0.3077),
     never NaN.
   - `FisherZTable::lookup_i8` returns code 0 for out-of-range centroids, which decodes to
     `z_min + 127/254·z_range` (cosine 0.64 under G2), not to a neutral value.
   - Encode is monotone (0 order inversions over 20,000 sorted inputs) but merges 19,743 adjacent distinct
     inputs. Ranking survives quantization; resolution does not.
7. **The TFLM reference itself aborts on flat rows.** `TFLITE_CHECK(0 <= exponent && exponent <= 31)`
   (`softmax.h`) kills the process once the row's sum of exponentials reaches 2^9.
   - Measured boundary: 511 tied maximal elements pass, 512 abort.
   - Probe: 14 of 120 cases aborted, with real sums ≥ 1,692; every passing case had a sum ≤ 478. They
     include n = 4096 uniform at β = 1 with only 18 ties.
   - A native port must not inherit this. It needs a wider accumulator or a pre-shift.
8. **Output saturation.** p ≈ 1 maps to TFLM code 127, i.e. 255/256, so the error is 1/256 at the top end.

### E6. The strongest valid statement

For one FamilyGamma per row and a softmax over `β·z` (path A):
- calibration is paid once (a 256-entry table per (β, z_range));
- no decode, tanh, per-element exp or atanh exists at run time;
- what runs is a code maximum, code differences, one gather and an integer add per element, and one
  normalization per row, or none for ranking, argmax and fused consumers;
- the binary case reduces to `q_1 − q_2`;
- it is exact over decoded representatives, and on the probe it is byte-identical to TFLM's int8 softmax
  whenever TFLM does not abort.

It stops at:
- mixed calibrations (E4.1);
- softmax over cosines or over non-affine palette indices, which become 64 KiB pair tables (E4.2-3);
- chaining a probability back into palette laws (E4.4);
- the original pre-quantization values (E1, E4.6);
- float parity (E5);
- denominators past TFLM's limit (E4.7).

### E7. Recommendation

No new kernel is justified. The algorithm already exists twice: as TFLM's int8 softmax (the reference)
and as a table plus integer sum built only from existing ndarray primitives (gather, integer add, max).

The smallest legitimate next step is a decision rather than code: whether the FisherZ consumers need
probabilities at all, or only ranking, a difference, or a fused weighted sum. In those cases nothing is
built.

If an int8 probability output is wanted, it belongs in the D-TFLP SOFTMAX stage, with:
- TFLM as the oracle;
- this probe's F = 24 table arm as the native candidate;
- a wider accumulator to remove the 512 abort.

The next falsifier is the same calibration sweep as for TANH (Amendment 3), looking for any byte where
the F = 24 arm and TFLM differ.

## Amendment 5 (2026-10-26) — precision: exact integers, ndarray FMA, and a selective f64 escape hatch

Probe: `.claude/probes/fisherz-softmax-v1/precision/` (Rust arms calling ndarray's real `simd::mul_add_f64`,
a 40-digit mpmath reference, 261 cases; a separate deskew experiment). Audit and probe only; no production
code changed. Correction to scope: `bgz-tensor::FamilyGamma` is a legacy reference, not a dependency; the
identities below are stated for any affine or monotone codebook.

### F1. ndarray's FMA, as implemented

- `simd::mul_add_f64` / `mul_add_f32` (`src/simd_ops.rs:154,168`) call `simd_fma::ExactFma`, and
  `simd_fma.rs:1-17` defines the contract: one rounding, to nearest-even, for every input. The
  realization depends on the target:

  | target | realization |
  |---|---|
  | x86 with `target_feature = "fma"`, and every aarch64 | hardware `mul_add` |
  | otherwise, f32 | computed in f64 with round-to-odd (Boldo-Melquiond) |
  | otherwise, f64 | integer arithmetic with a 128-bit window and a sticky bit (`simd_fma.rs:139-142`) |
  | WASM `F64x8::mul_add` | Dekker split + two-sum + round-to-odd inside a checked operand range (`simd_wasm.rs:2465-2481`); outside it, falls back per lane to the integer `fma_f64` (`:551-575`) |
  | NEON | `vfmaq_f32` / `vfmaq_f64` |

- `simd::add_mul_f64` (`simd_ops.rs:212`) is **element-wise** `acc[i] += a[i]·b[i]`, single-rounded per
  lane. It is not a dot product and has no reduction. A softmax-weighted sum is a reduction, so its
  ordering and accumulation error belong to the caller. The runtime twin `simd_runtime/add_mul.rs` has the
  same per-lane semantics, dispatched once by `LazyLock`.
- **Measured:** the baseline x86-64 build (no `fma` target feature, so the integer `fma_f64` runs) and a
  `target-cpu=native` build (hardware FMA) gave bit-identical results on all 261 cases. Cost is another
  matter (F5).

### F2. The identity, without FamilyGamma — and a correction to Amendment 4

For any representatives x(q):

  `e^{β(x_i − x_max)} = e^{β x_i} · e^{−β x_max}`

The second factor is common to the numerator and the denominator, so

  `p_i = E[q_i] / Σ_j E[q_j]`, with `E[q] = e^{β(x(q) − c)}` for **any** constant c.

- **Correction to Amendment 4 E4.2 and E4.3 (overclaims).** A nonuniform palette, and a softmax over
  cosines, need only a **unary** 256-entry table over representatives, not a 256×256 pair table. The row
  maximum is a dynamic-range device, not part of the mathematics. It matters only when the table is fixed
  point: with c fixed at the codebook maximum, a row whose maximum lies far below c keeps few significant
  bits per weight.
- **Affine codes** `x = a + s·q`: `E` depends only on `q − q_max`, so a fixed-point difference table with
  the row maximum loses nothing, and `a` cancels.
- **Common offsets.** Any common additive offset cancels exactly. With `EULER_GAMMA` added to every value
  the change measured `0.0` at 40 digits; a code-dependent offset of the same size moved p by 0.31.
  γ is not a softmax correction and was not used as one.

### F3. Results, 261 cases

Four codebooks: affine with step 0.0084 or 0.039; nonuniform normal or lognormal quantiles. β ∈ {1, 8},
plus β = 32 on the steep affine codebook. Row lengths 2-4096 across five distributions, and flat rows of
511, 512, 513 and 4096 tied maxima. V has four integer columns, including an alternating ±127 cancellation
column, and one real-valued column.

| arm | p max abs err | fused y max abs err | p output-code mismatches | y output-code mismatches | Σp − 1 |
|---|---|---|---|---|---|
| A: F24 weights relative to the row max (a pair table; on affine codebooks it equals the 256-entry difference table), exact u64 S and i128 N | 9.6e-5 | 1.2e-2 | 0 | 3 | exact |
| B: same F24 weights as f64 (exact), f64 sum, `mul_add_f64` dot | 9.6e-5 | 1.2e-2 | 0 | 3 | 6.7e-16 |
| M: B with separate multiply and add | — | 1.2e-2 | — | 3 | — |
| U: unary f64 table, codebook maximum as reference, no row max | 9.3e-14 | 1.2e-11 | 3,072 (all on the 512-tie rows) | 1 | 1.1e-13 |
| C: per-element f64 exp vs row max, Neumaier sums | 1.4e-16 | 2.5e-14 | 0 | 0 | 6.7e-16 |

Output codes: p uses TFLM's contract (scale 1/256, zp −128), y rounds to the nearest integer. Both round
ties away from zero; the reference code is computed from the 40-digit values.

- **A and B are the same arm.** F24 weights are integers below 2^53, so as f64 they are exact. Their
  error is entirely table rounding: weights below 2^-25 round to zero (up to 4,095 per row), the analogue of
  TFLM's `diff_min` cut. Accumulator widths measured: S ≤ 37 bits, N ≤ 38 bits (u64 / i128 suffice; i64
  suffices for N here).
- **Integer outputs can be rounded exactly from (N, S).** The quotient and remainder give the correctly
  rounded code of the arm's own rational N/S, with no float conversion at all. The 3 mismatches come from
  the weights, not the division: in each the reference lies within **7.3e-9** of a .5 boundary.
- **FMA vs separate multiply/add.**
  - On the integer columns the two are bit-identical: products of F24 weights and |V| ≤ 127 are exact, so
    fusing changes nothing.
  - On the real-valued column they differ in 58 of 261 cases, but FMA was closer to the reference in 26
    and further in 32. The worst error is identical.
  - One single-rounded multiply-add per step does not control accumulation error in a sequential dot
    product.
- **U loses exact ties.** Every 512-tie row has the true p = 1/512, which is exactly a rounding half
  (256 · 1/512 = 0.5). U's sum of 512 equal f64 weights is not exact, so p lands an ulp off and the half
  breaks the wrong way. Its single y mismatch is likewise a reference exactly on .5. A and B represent
  1/512 exactly; C's compensated sum does too.
- **Flat rows are not a problem for any arm.** 511, 512, 513 and 4096 tied maxima all produce the
  correctly rounded codes in A, B and C.

### F4. The TFLM abort, root cause

`softmax.h:115-119` computes `shifted_scale = GetReciprocal(sum_of_exps, 12, &num_bits_over_unit)`, then
`exponent = num_bits_over_unit + 31 − 8` and `TFLITE_CHECK(0 <= exponent && exponent <= 31)`.
`num_bits_over_unit` is the number of integer bits of the sum (`common.h:968-974`), so the check fails
exactly when the sum reaches 2^9.

- **It is a shift-range limit, not an accumulator overflow.** The final per-element step is an int32
  `RoundingDivideByPOT`, which cannot shift by more than 31.
- **Correct outputs do exist for such rows:** every p ≤ 1/512, so every code is −128 or −127.
- **Second, independent limit:** the Q12 sum itself overflows at 4,096 tied maxima.
- A native implementation must not reproduce the abort. Parity with TFLM is claimed only where the sum is
  below 2^9 (the Amendment 4 domain).

### F5. Cost (this host: x86-64 with AVX-512 and FMA; scalar loops over 4096-element rows; three runs; noisy)

| arm | baseline x86-64 build (software FMA) | `target-cpu=native` (hardware FMA) |
|---|---|---|
| A, difference table | 1.5-2.1 ns/elem | 1.6-2.5 |
| A, pair table | 2.0-2.8 | 2.0-2.2 |
| B, F24 + `mul_add_f64` | **31-36** | 1.7-2.0 |
| U, unary f64 + `mul_add_f64` | **33-37** | 1.4-2.0 |
| C, f64 exp + Neumaier | 11-16 | 8.7-14 |

- The correctly rounded software `fma_f64` costs about 20× the hardware instruction. A build without
  `fma` should not put `mul_add_f64` on a softmax hot path; plain integer accumulation is as accurate
  here and an order of magnitude cheaper.
- With hardware FMA, the integer and FMA arms cost about the same.
- Per-element `exp` (C) costs 4-7× more than any table arm.
- These are measurements of scalar loops, not of a vectorized kernel.

### F6. Palette deskew

Each of the four representatives tested is still one 256-entry table, so deskew is free at run time:
- bin midpoint;
- conditional mean;
- conditional median;
- log-mean-exp, `(1/β)·log E[e^{βt} | q]`: the value whose exponential is the bin's expected weight.

Error is measured against the softmax over the true held-out values.

- **Bounded skewed source** (2·Beta(2,5) − 1, cosine-like), β = 4, n = 4096:
  - total variation 0.0515 (midpoint) → 0.0210 (conditional mean) / 0.0215 (log-mean-exp);
  - weight-sum bias +5.6% (midpoint) → −0.37% (mean) / **+0.13% (log-mean-exp)**.
  - At β = 1 every corrected representative beats the midpoint as well (TV 0.0019 → 0.0012).
  - Log-mean-exp is the least biased for the denominator, as Jensen's inequality predicts; the
    conditional mean is as good or slightly better for TV. The correction is **β-dependent** for
    log-mean-exp.
- **Heavy-tailed source** (lognormal): no correction helps. The open-ended top bin of an
  equal-probability codebook holds the row maximum, so TV is 0.81-0.91 at n = 4096 whatever the
  representative, and the weight-sum bias diverges. This needs a codebook with tail resolution, not a δ.
- **Codebook versions:** two calibrations of the same distribution (400k samples each) gave matching
  results when the tables were swapped. Version keying (the recipe receipt) is still required, but this
  probe did not demonstrate a harmful mismatch.

### F7. Decision

- **Default.** Prepared table + exact integer accumulation (A) meets the int8-output contract on every
  case except references within 7.3e-9 of a rounding half. It needs no floating point until the output
  boundary, and none at all for integer outputs.
- **Escape hatch.** The error of A is bounded by its table rounding; an explicit bound is derivable from
  F and n. When the integer result falls inside that bound of a rounding half, recompute that row with C.
  This is per row and amortized; it removes all mismatches observed. The bound and its trigger rate have
  not been measured yet.
- **FMA is not needed** for A's integer path and gave no accuracy benefit on these reductions. Use it where
  operands are genuinely real-valued and a single multiply-add is the operation.
- **Unary f64 tables (U)** are the natural form for nonuniform or deskewed palettes. Avoid them where exact
  ties matter, or sum their weights exactly.
- **Deskew** is worth it for bounded skewed codebooks and costs nothing at run time; it does not fix tail
  resolution.

**Smallest justified next step:** none in production yet. The next probe is the escape-hatch bound — derive
it, measure how often it triggers, and confirm that it catches every mismatch — together with the
calibration sweep against TFLM already named in Amendments 3 and 4.

### G1. The certified F24 bound — probe result

Probe: `.claude/probes/fisherz-softmax-v1/precision/cert.py`, run recorded in `cert.json`.
It uses the same generator, seed and 261 cases as Amendment 5, and the same 40-digit mpmath
reference. Wall time: 33 s.

**Method.**
1. **Table build.** Every F24 entry `W = round(2^24 · e^{β(x_a − x_m)})` is evaluated in
   outward-rounded interval arithmetic at 96 bits. An entry counts as certified when its interval
   cannot straddle a .5 point. This proves `|2^24 w − W| ≤ ½`, the hypothesis of ledger entry G.
2. **Arm A in exact rationals.** Compute `ŷ = N/Ŝ` and `p̂ = W/Ŝ`, then the ledger G bound on each.
3. **Certification.** An output is certified when the code is the same at both ends of its bound.
4. **Escalation.** Any row with an uncertified output is recomputed by the ledger H resolver:
   - exact rationals for a single representative;
   - the exact-rational-y test for equal group means;
   - otherwise intervals at 64, 128, 256 and 512 bits, stopping at 512 as UNRESOLVED.

**Results (all 261 cases).**

| quantity | value |
|---|---|
| outputs | 1,305 y + 247,473 p = 248,778 |
| table entries not certified to ½ | 0 |
| entries where an ordinary f64 `math.exp` generator disagrees | 0 |
| `Ŝ > E` (bound defined) | 261 / 261 rows |
| outputs certified directly | 1,299 y, 242,865 p |
| **misses** (certified but wrong code) | **0 y, 0 p** |
| arm-A wrong codes before escalation | 3 y, 0 p (the Amendment 5 three, each within 7.3e-9 of a half) |
| rows escalated | 13 / 261 (5.0%) |
| uncertified outputs | 6 y + 4,608 p (1.85% of all outputs) |
| uncertified outputs where A was already right (false alarms) | 4,611; 4,608 of them on the nine 512-tie rows |
| how the escalated rows resolved | 10 exact-rational, 3 interval at 64 bits, 0 unresolved |
| **final wrong codes after escalation** | **0 y, 0 p** |
| largest y bound | 1.55e-2 |

- **The false alarms on tie rows are forced.** On those rows `p = 1/512` exactly and
  `256 · p = ½`. A bound of nonzero width around an exact midpoint can never certify. The
  exact-rational path is what resolves them, and it gives the right code on every row.
- **The cost below is Python lab cost, not kernel cost.** It shows the ratio between the two paths
  and nothing about a production implementation.

  | path | median s/element | worst row |
  |---|---|---|
  | base (arm A + bound) | 9.9e-5 | 0.48 s |
  | escalation | 1.65e-5 | 0.18 s |

**The fallback implements the declared rounding rule (ties away from zero, TFLM's output rule).**
- **Exact-rational path.** It applies the rule to the exact value, so it is correct by construction.
- **Interval path.** It returns only when both ends give the same code. The exact value lies
  between them, so the result is that value's code whatever the tie rule. The path therefore
  never decides a tie.
- **When a tie can happen.** β and the representatives are f64, hence rational.
  Lindemann–Weierstrass then gives:
  - p is irrational whenever the row has two or more distinct representatives;
  - y is rational only when every distinct-representative group has the same V-mean, and that
    case is caught exactly before the interval path runs.
- **Consequence.** Every row the interval path receives has an irrational value and terminates at
  finite precision. 512 bits is a practical cap; reaching it fails closed, it is never a guess.
- **Disable run.** With the equal-means test removed, the control below came back
  `UNRESOLVED` at 512 bits. With it, the result is code 3, which matches the reference. The test is
  load-bearing.

**Negative controls (all executed).**

| control | result |
|---|---|
| NaN or ±inf representative | refused at table generation |
| β ∈ {0, −1, NaN} | refused |
| wrong codebook, no identity check | **the bound certifies a wrong code** (claims 2, reference differs). The bound is conditional on table identity. |
| wrong codebook, with the digest check (sha256 of representatives + β + F + rounding) | refused; the digests differ |
| exactly rational y on a midpoint with two representatives (group V-means both 5/2) | resolves to code 3 = reference |
| saturation | covered by the clamped codes of the 4096-length and spike rows; no separate control |
| mask (elements excluded before the max and the sums) | reference-side shape check only; **no arm consumes a mask** |

| policy | placement | reason |
|---|---|---|

1. **OBSERVE** — collect value statistics per code; no table changes.

changes model weights.** Model learning is out of scope for this staging. A codebook is never
mutated in place.

## Amendment 6.2 (2026-10-26) — source-behavior preservation, prepared transcoding, certified LUT composition

### K0. Architectural clarification

A pure, finite-code unary operator can be prepared once as its complete output mapping, and
then executed by lookup with no source runtime. Three **semantic contracts** follow. They are
receipts on a prepared artifact, not new Rust types or runtime modes:

| contract | question it answers |
|---|---|
| `SourceParity` | Did we produce exactly the bytes this pinned source implementation produces? |
| `CertifiedMath` | Did we satisfy the operation's declared mathematical and rounding contract? |
| `AdaptivePrecision` | What is the cheapest method that satisfies the consumer's required contract? |

- **They answer different questions.** A source can be historically imperfect, and parity with it
  is still useful. A more accurate implementation can still break byte parity with an older
  model. Neither is preferred by default, and neither may impersonate the other.
- **Nothing here supports a claim about TFLite adoption.**
- **"Roundtrip" is not the cause of the 17 discrepancies.** K1 shows the int8 path has no float
  decode/encode at all.

Ledger D-PAL256-ALG-1 entry **K** carries the definitions:
- `L_math[q] = Q_out(f(D_in(q)))`;
- `L_src[q] = K_src(q)`;
- the fingerprint `Δ = L_src − L_math`;
- the finite-domain equivalence proof, the composition theorem, and their restrictions.

### K1. Source-level TANH discrepancy trace

### K6. Runtime identity and calibration requirements (documentation only)

The minimum a prepared table must eventually be bound to:
- **Source identity:** framework, kernel implementation and path, kernel tree revision,
  operator, version, backend (TFLM reference ≠ CMSIS-NN ≠ xtensa ≠ full TFLite).
- **Interpretation:** storage, code space, input and output scale and zp (per-axis or per-block
  where they apply), rounding, saturation, NaN, inf, and signed zero where observable.
- **Artifact:** the complete table (or an authenticated reconstruction), its full digest, the
  calibration generation, the contract, every intermediate quantization boundary for a fused
  table, provenance, preparation version, and validation evidence with its independent
  reference.

Artifact identity and semantic identity are separate: 2,215 calibrations here have equal bytes
under two different contracts. A new calibration means a new generation and a new validation.
Active semantics are never mutated in place.

### K7. Learning and IR boundaries (documentation only)

- **Learning.**
  - Byte parity in the forward pass is not gradient parity. Quantized operators are
    nondifferentiable at their rounding boundaries, and a fused table carries none of the
    source's backward pass, straight-through estimator, surrogate gradients or optimizer state.
  - Learning admission is a separate future gate. No gradients were invented here.
  - Calibration staging (OBSERVE → PREHEAT → PROPOSE → VALIDATE → COMMIT) regenerates both tables
    per generation.
- **TFLite / TFLM.**
  - Operator versions, quantization parameters, kernel numerics and backend identity are kept.
  - One pinned TFLM reference backend does not give "TFLite parity".

**Relation to TANH (measured, not assumed).** The kernel's exp raw value is the same integer as in

two operators at one argument; it is not a claim about any other argument.

**Scope of the LOGISTIC fingerprint at (1/128, 0).** Source vs certified tables differ at
intermediate codes −1 and +1 only (`logistic_source_vs_certified_codes`).

#### M3. Signed-overflow boundary (softmax accumulation)

- **Add.** `fixedpoint.h:91-95`: `// Integer addition. Not saturating. Overflow is undefined
  behavior.` `Add(a, b) { return a + b; }`. This is the `sum_of_exps + Rescale<12>(…)` of
  `reference/softmax.h:109`.
- **Range.** Each admitted weight is `Rescale<12>(exp)`, at most `Rescale<12>(One) = 524,288 = 2^19`
  (exp ≤ 1; measured B[0] = 524,288). The partial sums are monotone non-decreasing and
  non-negative. So a row overflows int32 iff its exact sum exceeds INT32_MAX, which first happens
  at 4,096 maximal elements (4,096 · 2^19 = 2^31).
- **Guard order.** The abort guard (`softmax.h:119`) runs **after** the loop, so it cannot prevent
  the overflow.
- **Inside the admitted domain** (real sum < 512, i.e. S < 2^28 raw) no partial sum exceeds 2^28,
  so no signed overflow is reachable. This is a derivation, not a sanitizer result. UBSan was
  additionally silent on all 729 admitted corpus rows and on all TANH/LOGISTIC calibrations.
  Silence is not proof; the derivation is.
- **Outside the domain**, measured (`backend63.json` → `overflow_rows`):

| ties n | exact sum | wrapped int32 S | ordinary builds (all 5) | UBSan (signed overflow) | UBSan (shift) |
|---|---|---|---|---|---|
| 4,095 | 4,095 | no wrap | abort (exponent) | abort (exponent) | abort |
| 4,096 … 8,191 | ≥ 2^31 | negative | abort (exponent 35) | **signed-overflow report**, `fixedpoint.h:94` | abort |
| 8,192 | 2^32 | **0** | **completes, all −128** | signed-overflow report | **shift report**, `common.h:976` (`<< 32` on uint32) |
| 8,193 | 2^32 + 2^19 | 2^19 (= 1.0) | **completes, all 127** | signed-overflow report | completes, all 127 |
| 8,194 | | 2^20 | completes, all 0 | report | completes |
| 8,300 / 8,703 | | admitted range | completes, −126 / −127 | report | completes |
| 8,704 / 12,288 | | exponent > 31 | abort | report | abort |
| 16,384 / 16,385 | | 0 / 2^19 | completes, −128 / 127 | report | shift report / completes |

- **The true answer** for n tied inputs is ≈ 256/n − 128 → −128 for every n here. So n = 8,193
  returning 127 everywhere is a **confident wrong result**, not an abort.
- **Across builds.** All five ordinary builds produce identical bytes on these rows (wraparound in
  practice). That is an observation of five artifacts, not a property of the source: the language
  gives no meaning to the add, and n = 8,192 has a second undefined shift.
- **Classification:** `UNDEFINED_OR_UNSUPPORTED`. The 6.3 recipe refuses these rows
  (`q12_accumulator_overflow` when S > INT32_MAX). It never reproduces a wrapped result.
- **Pinning.** If a consumer ever needs those bytes, they belong to an explicitly pinned
  nonportable artifact (compiler, flags, target named). They are never part of a portable source
  contract.
- **Not run:** a 64-bit-int sum variant of TFLM, and other compilers' optimisation of the UB add.

#### M4. Reciprocal observability

- **The question.** Within the admitted softmax domain (6.3 L3), can replacing only the source
  reciprocal (`GetReciprocal`, `common.h:968-982`) by a correctly rounded one,
  `round(2^62 / (S << headroom))`, change an output byte? Every other stage stays the source's.
- **Reduction (from `reference/softmax.h:115-139`).** For a fixed calibration, an admitted output
  byte is a function of (S, A[d]) only. The search space is therefore every row sum S in
  [B[0], 2^28) (the max element contributes B[0], and exponent ≤ 31 ⇔ S < 2^28) × every distinct
  admitted weight. This is a superset of all reachable (S, d) pairs.

**Exhaustive superset (`recipall63.cc`, `recipall63.json`).** 14 calibrations, 3,750,756,352
values of S (23 min on 3 cores):

| measure | count |
|---|---|
| S where source and exact reciprocal differ | 3,281,945,604 (87.5 %) |
| (S, weight) pairs where the output byte changes | **601**, in 13 of 14 calibrations |
| calibration 9 (scale 0.5, zp −25, β 2.0) | **0 pairs**: the substitution is output-equivalent on that calibration's whole admitted domain (`PROVED` by exhaustion) |

**Reachability (`reach63.cc`, `reach63.json`).** A pair is only a candidate until an int8 row has
exactly that sum and contains the element. The solver (an unbounded min-coin DP over the admitted
weights) built rows for **529 of 601** candidates. All 529 were run through the real TFLM kernel,
and each is an **authentic witness**: the kernel byte equals the source-reciprocal byte and differs
from the exact-reciprocal byte.

- The independent 6.3 Python recipe (`reachcheck63.py`) reproduces both bytes on all 529.
- The 72 remaining candidates are `UNKNOWN`: no row was found, which does not show that none
  exists.
- Witness rows are 4 to 507 elements long, with Δ = −1 on 279 and +1 on 250.

**Shortest witness:** calibration 10 (scale 1/256, zp 20, β 1.0), row `[127, 1, −2, −90]`. The
kernel gives `[−31, −69, −69, −87]`. The element −2 (difference −129) is −69 from the kernel; the
correctly rounded reciprocal gives −70.

**Negative control.** A deliberately perturbed reciprocal (source + 256 raw units) on calibration 0
changes 3,037 pairs (`recipall63_control_delta256.json`), so the detector can see a reciprocal
change.

**Classification.** Replacing the source reciprocal is `OUTPUT_DIVERGENT` on the admitted domain
(13 of 14 calibrations have reachable witnesses) and `OUTPUT_EQUIVALENT` on calibration 9.
SourceParity therefore requires the source reciprocal, which the 6.3 recipe keeps. The 6.3 corpus
simply contained no witness row. Its 1.8 M two-level family search (`recip63.json`) found 0
witnesses, a statement about that family, as 6.3 L3 said.

**Two-level rows cannot carry a witness on this evidence.** The two-level family
`[max]*k + [max+d]*m` was also searched natively (`recipwit63.cc`):
- m ≤ 64: 82,393,847 rows, 0 witnesses, nearest product 11 raw units from a rounding half
  (`recipwit63.json`);
- m ≤ 8,192: 5,724,274,337 rows, 0 witnesses, nearest margin 1 raw unit.

The m ≤ 8,192 JSON was overwritten by the m ≤ 64 rerun, so only its header numbers survive. They
were read from the file before it was overwritten. Every witness the solver built uses at least 4 distinct
codes. This is the solver's construction, not a proof that no 2- or 3-code witness exists.

#### M5. Error propagation, TANH → LOGISTIC (`prop63.json`; the 6.3 four-arm counts unchanged)

- **Large internal error, small observable effect.** LOGISTIC at (1/128, 0) has no saturated code
  (radius exceeds the code range).
  - The kernel's exp value is off by more than 0.5 raw unit on **214 of 256** codes; the range is
    −355.7 to +472.3 Q0.31 units.
  - The pre-rounding output value is off on **243 of 256** codes, by up to 148.9 units, which is
    1.8·10⁻⁵ of an output step.
  - **2** output bytes differ from the certified table.
- **Small upstream error, amplified by fan-in.** Those 2 wrong LOGISTIC entries (codes −1 and +1)
  are read by every input whose TANH code lands on them:
  - 48,806 fused cells in total;
  - 0 in 1,139 of 2,224 calibrations and up to 171 in one;
  - median distinct intermediate codes per calibration 17;
  - largest single-code fan-in median 109, maximum 256.
- **TANH's own error.** 17 cells are visible after stage 1.
  - Hidden by a certified LOGISTIC in all 17 (SC ≡ CC).
  - Preserved by the source LOGISTIC in all 17 (SS ≠ CS).
  - Cancelled: 0.
  - Amplification of TANH's error itself: 0. Its 17 cells are 17 inputs each.
- **Consequence for adaptive precision.** The cost of an error is (internal error × probability of
  crossing a rounding boundary × fan-in of the affected code), not the internal error. The
  measurement that matters is per code, after quantization.

#### M7. Artifact identity

- **Shared table bytes, separate receipts.** On the tested corpus the six x86 builds produce
  byte-identical TANH/LOGISTIC tables and softmax bytes. A SourceParity table prepared from one of
  them is therefore valid for all six, with the same digest.
- **What the receipt records.** It must name the build set actually verified (source revision,
  kernel path, compiler and flags, ISA). A backend not in that set needs its own run:
  - **same bytes:** the same digest, and the receipt gains a verified backend;
  - **different bytes:** a separately identified artifact.
- **No per-backend artifacts by default.** None are needed where outputs agree, and none were
  created.
- **Execution is backend-independent once prepared.** The native execution form (`table[code]`,
  or the integer recipe) has no backend dependence. The dependence lives entirely in how the
  table was prepared and verified.

## Amendment 6.4 (2026-10-26) — signed/unsigned SIMD, −128, and quantization semantics

Scope: source audit, lab probes and documentation. No production kernel, Codec8 API, model data
or runtime was changed, and Amendment 6.3's artifacts and results are unchanged. Lab commit:
`383e9c07c`, `.claude/probes/int8-semantics-v1/` (build and run lines in its `README.md`).
- TFLM: the 6.3 checkout `5f64e4ad`, baseline library.
- ndarray: `11954d7d`.
- Host: Xeon @ 2.10 GHz with AMX-INT8, AVX-512 VNNI, AVX-VNNI and AVX-512 VBMI.

The question is whether each byte means the same number in the source reference, the ndarray
scalar path and the ndarray SIMD paths, including −128, −1 and 0. A second question is whether
the rounding stages reproduce the source's own rules.

### N1. Four statements, kept apart

1. **Weight format.** Conforming TFLite symmetric weights are quantized to −127..127. This is a
   model-format rule.
   - TFLM itself does **not** enforce it. The int8 FC prepare guards only the weight zero point,
     and only with a debug check: `TFLITE_DCHECK(filter->params.zero_point == 0)`
     (`kernels/fully_connected_common.cc:147`). No value-range check exists.
   - The conv/depthwise accumulator comment assumes the range: "accumulation is [-127, 127] *
     ([-128, 127] - [-128, 127])" (`reference/integer_ops/conv.h:105-109`,
     `depthwise_conv.h:90-94`).
2. **Activations and nonlinear outputs** use −128..127; −128 is a value.
3. **TFLM reference arithmetic** multiplies whatever int8 it is given, −128 included:
   `acc += filter_val * (input_val + input_offset)` (`reference/integer_ops/fully_connected.h:64`).
4. **ndarray SIMD** may use a different physical operand (u8 = i8 + 128) and must correct for it.

Statement 1 says nothing about statements 3 and 4, and the probe treats them separately.

**Where A ≠ D comes from** (`fcattr64.py`, per cell):
- **416 conforming and 354 extended cells: double rounding.** TFLM rounds in SRDHM and again in
  `RoundingDivideByPOT`. The single-rounding formula with the same multiplier gives the exact
  answer. Multiplier quantization contributes 0 cells.
  - Example: `C1_pc0_izp0_ozp-128`, acc 6,119, mult 1,628,303,079, shift −6 → exact 72.49… → 72;
    TFLM 73.
- **837 tie cells: negative half ties.** SRDHM's nudge `1 − 2^30` rounds a negative half toward +∞:
  acc −15 × 0.5 = −7.5 → TFLM −7, ties-away −8. Positive ties agree. This is the documented
  `srdhm_i32` behaviour (`simd_fixedpoint.rs:35-43`), which ndarray reproduces.
- **2 cells at the output clamp boundary,** also double rounding.

**Classification.** A vs D is source numerical deviation, not a port defect. A = B = C is
SourceParity, held for both suites. The extended suite is labelled an extension: TFLM's reference
arithmetic is defined on −128 weights and both ndarray paths match it, but no conformance is
claimed.

### N8. Missing seams (smallest genuine gaps; no new kernels proposed)

1. **Code-space identity does not travel with the bytes.** `Asym` and `Sym+NaNAtMin` both take
   `&[i8]`, so a numeric −128 reaches a NaN decoder unchallenged (F4). The receipt that binds a
   prepared recipe must carry storage, code space, NaN policy, rounding, scales/zero points and
   the codebook generation (already listed in 6.2 K6). No runtime dispatch is proposed; the gap
   is at the binding, not in Codec8.
2. **The raw-byte convention is unmarked.** `simd_avx2::dot_i8(&[u8], &[u8])` means raw i8 bytes,
   while Codec8 `U8` means biased. A caller can join them silently (N3). A test or a doc
   cross-reference would mark it; the API is not changed here.
3. **The i32 accumulator contract is implicit.** `matmul_i8_to_i32`'s correctness precondition
   (true result fits i32; wrapping arithmetic) is not stated. Debug builds panic on in-range
   inputs on the SIMD tiers only. The fix would be `wrapping_*` in `subtract_i8_to_u8_bias` plus a
   stated precondition, a production change not made here.
4. **A wrong doc bound:** `simd_int_ops::dot_i8`'s "4M lanes" claim (the real bound is 131,071
   lanes in the worst case).
5. **No differential test in ndarray against TFLM.** This probe is the only one. The
   2,009,224-case fixed-point corpus and the FC four-arm harness are candidates to become
   committed fixtures.

#### N11. Source-domain / portability gate (separate from SourceParity)

SourceParity is a claim about the source's *defined* behaviour on an *admitted* domain. Six builds agreeing
(6.3 addendum M2) is evidence for those six artifacts. It cannot extend parity to rows where the C++ source
has no defined meaning. Every softmax row therefore passes this gate first, and lands in exactly one class:

| class | meaning | consequence |
|---|---|---|
| SUPPORTED | no undefined operation is reachable and no source guard fires | byte parity is meaningful and claimed |
| UNSUPPORTED | a source guard aborts deterministically (defined behaviour) | typed refusal; no byte claim |
| UNDEFINED | a C++ operation with no defined result is reachable | refusal; bytes some builds return are **not** part of any contract |

**Exact source guards and undefined operations, int8 SOFTMAX (TFLM `5f64e4ad`):**

| site | operation | defined when | otherwise |
|---|---|---|---|
| `softmax_common.cc:128-130` → `quantization_util.cc:339-355` | `diff_min = −floor(31·2^26 / 2^left_shift)` | always | — |
| `reference/softmax.h:103` | `if (input_diff >= diff_min)`: element admitted | — | element outputs −128, independent of the row sum |
| `common.h:396-400` | `x * (1 << left_shift)` on an admitted difference | \|d\|·2^left_shift ≤ 31·2^26 < 2^31, guaranteed by the radius | not reached (element not admitted) |
| `reference/softmax.h:109` → `fixedpoint.h:91-95` | `sum_of_exps + Rescale<12>(…)`, plain int32 `a + b`, comment "Overflow is undefined behavior" | exact sum ≤ INT32_MAX | **UNDEFINED** (signed overflow); no guard runs before it |
| `common.h:970-977` (`GetReciprocal`) | `uint32(x) << clz(x)` | x ≠ 0 (shift ≤ 31) | **UNDEFINED** at x = 0 (`<< 32`) |
| `reference/softmax.h:118-119` | `TFLITE_CHECK(0 <= exponent && exponent <= 31)`, exponent = 35 − clz(S) | passes for 0 ≤ S < 2^28 (S = 0 gives clz 32, exponent 3: it passes *after* the undefined shift) | **UNSUPPORTED** (abort) for S ≥ 2^28 or S < 0 — it runs after the sum, so it cannot undo an overflow, and it does not catch S = 0 |
| `fixedpoint.h:357-358` | `assert(0 <= exponent <= 31)` in `RoundingDivideByPOT` | compiled out under `NDEBUG`; unreachable once the CHECK passed | — |

**Admitted domain (derivation).** A row is SUPPORTED iff its exact admitted-weight sum S satisfies
2^19 ≤ S < 2^28. The lower bound comes from the row maximum (weight Rescale<12>(1) = 2^19). In that range
every partial sum is non-negative, monotone and ≤ S < 2^31, so no add overflows. S ≠ 0, so the shift is
defined, and the exponent lies in [23, 31], so the CHECK passes. The output tail (`SaturatingRoundingDoublingHighMul`,
saturating; `RoundingDivideByPOT` with exponent ≤ 31 on x ≤ INT32_MAX, whose `+1` occurs only for exponent ≥ 1,
i.e. x>>exponent ≤ 2^30; `+ (−128)`; clamp) has no undefined operation either. This is a proof over the
source text, not a sanitizer result.

**Minimal counterexamples (proved minimal).** Every admitted weight is ≤ 2^19.
- Signed overflow needs exact sum > 2^31 − 1, so at least 4,096 admitted elements; **4,096 maxima** is
  minimal and reaches `fixedpoint.h:94`.
- The undefined shift needs a wrapped sum of exactly 0, i.e. exact sum a positive multiple of 2^32, so at
  least 8,192 admitted elements; **8,192 maxima** is minimal and reaches `common.h:976`. It can only be
  reached after an overflow, so it is UNDEFINED twice.
- Between them, 512 … 4,095 maxima are UNSUPPORTED (exponent 32 … 34, CHECK aborts, defined).
- The confident wrong bytes of 6.3 addendum M3 (8,193 maxima → all 127; 8,300 / 8,703 → −126 / −127) are
  UNDEFINED rows. Their agreement across five builds is an observation of artifacts, never parity.

**Sanitizer evidence (`ubsanctl64.txt`, `recipall64_ubsan.json`).**
- Can-fire control, same flags as below (`-O1 -fsanitize=undefined -fno-sanitize-recover=undefined`):
  `add` (4,096 maxima) → `fixedpoint.h:94:14: signed integer overflow`, exit 1; `shift` (`GetReciprocal(0)`)
  → `common.h:976:54: shift exponent 32`, exit 1. Can-stay-silent: `none` (511 maxima) → exit 0.
- The whole admitted superset under UBSan: `recipall63.cc` and `trace63.cc` rebuilt with those flags
  (against `gen_ubsan/`) ran every S in [2^19, 2^28) × every admitted weight of all 14 calibrations, plus the
  exp stage for every difference: **0 sanitizer reports** over 3,750,756,352 S values (44 min on 3 cores; with `-fno-sanitize-recover` any report aborts the run, and every process exited 0), and the result is identical to the unsanitized run: the same 601 candidates, the same per-calibration counts. The derivation above is the proof; the run shows the
  build has no surprise on the tested calibrations.
- **Not covered:** other calibrations' `left_shift` values (the radius argument covers them; no run did), and
  compilers whose optimiser exploits the undefined add before the CHECK.

**Rule.** Every SourceParity statement in Amendments 6.2 – 6.4 (6.3 L3, addendum M2, M4, M6, N12, N13 below)
is restricted to SUPPORTED rows. UNSUPPORTED and UNDEFINED rows are refused with the guard named, and a
recipe never reproduces a wrapped sum or a post-overflow byte. If a consumer ever needs those bytes, they
belong to a pinned, named, non-portable artifact (6.3 addendum M3, unchanged).

**Why the superset covers every admitted case.**
1. A SUPPORTED row has S ∈ [B[0], 2^28) (N11).
2. An admitted element's byte depends only on (S, A[d]): the reciprocal and exponent are functions of S,
   the weight is a function of d (`reference/softmax.h:115-139`).
3. A non-admitted element outputs −128 whatever the reciprocal (`softmax.h:143-145`).
4. Rows have no length limit in the superset: only S is bounded, and S < 2^28 is exactly the admission bound.
**Why the tested computation is the source's.** `recipall63`'s `out_byte` calls the same header functions
(`SaturatingRoundingDoublingHighMul`, `RoundingDivideByPOT`), with the same exponent (`nb + 23`), offset and
clamp as `softmax.h:124-142`, and `GetReciprocal` itself for the source arm. It reproduced the kernel byte on
all 529 witness rows. So exhaustive absence of a candidate on a calibration is output equivalence on its
whole SUPPORTED domain: **calibration 9 stays PROVED equivalent**; the other 13 are **OUTPUT_DIVERGENT**
with reachable witnesses.

**Reachability is exact, not searched.** B[0] is itself a weight, so R is representable iff
R ≥ minrep[R mod B[0]], where minrep comes from Dijkstra over the residue graph mod B[0] (`reach64.cc`).
- Cross-check: a plain unbounded-coin DP over [0, 2^21] agrees with the residue rule on every value, 0
  mismatches in all 14 calibrations (`reach64_xcheck.txt`). All 32 gap cases (calibrations 10, 11) have
  S ≤ 1,692,428, inside that checked range.
- All 529 pairs reach63 had built are reachable again; none of reach63's 72 unknowns is reachable.
- **Disable run (and a defect it found in the witness check).** With the gap test removed, the solver
  emitted rows with negative multiplicities for the 32 gap pairs, and **15 of them passed as kernel
  "witnesses"**: the row actually built had a different sum, and the check compared only bytes. The solver
  now refuses negative counts (exit 7, the disable run fails loudly), and the driver recomputes each row's
  sum from the admitted weights and requires it to equal S before the kernel runs. The 6.3 reach63 witnesses

#### N13. Pruning around the final quantization boundaries (`recipprune64.*`)

For fixed weight w and exponent ex, the output byte is a non-decreasing step function of the reciprocal sh:
unsat ≥ m + 1 iff sh ≥ T_m = ⌈(β_m·2^31 − 2^30)/w⌉ with β_m = m·2^ex + 2^(ex−1), and only the steps
m = 0 … 254 are visible (unsat ≥ 255 clamps to 127). The two arms give different bytes iff some T_m lies
between them. With E_h = max |sh_src − sh_exact| over exponent band h, a differing byte needs
sh_exact(S) ∈ [T_m − E_h, T_m + E_h]. sh_exact is non-increasing in S within a band, so that is one S
interval per (w, h, m), found by binary search.

- **Measured bound:** E_h = 6 in every band h = 4 … 12, from a scan of the reciprocal alone over all
  S ∈ [2^19, 2^28) (no weight loop); monotonicity of the exact reciprocal asserted on every step.
- **Result:** the pruned candidate set equals the exhaustive one, **601 = 601, 0 missed, 0 extra**,
  evaluating **4,078 (S, weight) pairs** instead of 3,750,756,352 S values × every weight. Wall time 7.2 s,
  most of it the bound scan, against 23 min on 3 cores for the exhaustive run.
- **The window binds** (`recipprune64_window_sweep.json`): window 0 → 494 missed, 1 → 295, 2 → 148,
  3 → 26, 4 → 2, 5 → 0, 6 (the measured bound) → 0. That 5 already suffices on this data is an observation;
  only E_h is a proof.
- **Negative control preserved:** the δ = 256 mutation detector. Re-run exhaustively on calibration 0 with
  every candidate listed (`recipall64_control_delta256_full.json`; the 6.3 file kept 10 samples): 267,911,168 S values, the perturbed reciprocal differs from the source on 267,911,159 of them, and **3,037** (S, weight) pairs change a byte, the same count 6.3 recorded.
  The pruned search with window E_h + 256: **the identical 3,037-pair set** (0 missed, 0 extra) from 6,351 evaluations (`recipprune64_control_delta256.json`). The pruning therefore sees a reciprocal change the exhaustive detector sees, and loses nothing under a mutation that is 40× its own error bound.
- **Scope.** Soundness rests on E_h being the true maximum (measured by exhaustion of the reciprocal, which is
  calibration-independent) and on the exact reciprocal's monotonicity (asserted). The pruning is a second,
  independent derivation of the exhaustive result, not a replacement for it on new calibrations unless both
  conditions are re-checked there.

### O1. Semantic identity: what do these bytes mean? (P0)

**Where the identity is lost (traced, `ndarray` `src/hpc/codec8.rs`).** A codec's meaning lives only in
its type parameters: `Codec8<T: Storage, S: CodeSpace, R: Rounding, N: NanPolicy>` plus a `Calibration`.
`decode_checked` takes a bare `&[T::Elem]`.

- The chain *logical code space → encoding/storage → prepared artifact receipt → consumer binding →
  decode* breaks at the second arrow. Once encoded, the bytes carry nothing.
- **There is no production seam.** Outside `codec8.rs`, `Codec8` is used only by three lab probes
  (`int8sem`, `crossdot`, `source-behavior-v1/parity`) and `examples/codec8_asm_probe.rs`. No lance-graph
  crate consumes it.
- The binding store is MISSING (`d-native-repr-contract-v1.md` S5).
- The intended integration point is the **native method binding and recipe receipt** of
  `d-nam-palette-native-lut-capstone-v1.md` (lines 38–40, step PZL-4). That step already requires that two
  same-shape layers with different weights or calibration refuse the wrong table.

**The decoder is correct.** `Codec8<I8, Sym, TiesAway, NaNAtMin>` decoding −128 as NaN is its declared
policy. Nothing in `codec8.rs` was changed or proposed.

**Smallest safe contract, built as a lab adapter** (`pal256-admission-v1/admit/`):

- **No registry.** A codec's identity is a `CodecSignature` derived from `Codec8`'s own sealed traits:
  - `CodeSpace::MIN/MAX`;
  - `NanPolicy::NAN_CODE`;
  - the raw bytes `Stores::store` writes for −128 and 0, which separate I8 from biased U8;
  - `Rounding::round` on 0.5, 1.5, 2.5 and −0.5, which separates TiesAway, TiesEven and Floor.

  Two codec types with equal signatures behave identically; unequal ones differ on some input.
- **The receipt** carries:
  - the codec signature, which covers the logical code space, storage, NaN policy, rounding, and
    saturation (the code range);
  - scale bits and zero point;
  - the operator contract;
  - the codebook generation;
  - an optional source identity (revision and backend, for SourceParity);
  - the length;
  - the SHA-256 of the payload.
- **`bind(artifact, expect)`** checks length and integrity, then signature, calibration, operator,
  generation, source, then the payload's code range, in that order. It refuses with a named `Refusal`
  before any value is interpreted.
- **Binding happens once.** A `Bound` view then decodes through the consumer's own codec, with no
  per-element check added to the hot path.
- **Byte equality is not identity.** `bind` compares receipts, so identical bytes with different receipts
  bind to different consumers.

**Positive tests (TESTED, `tests/admission.rs`):**
- P1/P2: Asym −128, −127, −1, 0, 127 decode to their numbers.
- P3: SymNaN −128 decodes to NaN.

### O2. Integer exactness: the i32 accumulator contract (P0.5; separate from O1)

Four quantities, kept distinct:

1. **The mathematical accumulator** Σ q·w: exact in i64. The 6.4 i64 oracle computes it.
2. **The intended modular intermediate:** the biased u8×i8 sum and `128·colsum` may exceed i32. VPDPBUSD
   and TDPBUSD wrap by design, and the correction is exact mod 2^32.
3. **Final i32 representability:** the result equals the true value iff the true value fits i32.
4. **Native output acceptance:** whether a caller may use the value. Nothing checks condition 3 today; it
   is a documented-nowhere precondition (6.4 N8.3). **It is not enforced.**

**Measured (`f9wrap65.txt`).** Six cases, against the current ndarray and against a worktree with
`accum_wrapping65.diff` applied, each in debug and release:

| case | final fits i32 | current debug | current release | proposed debug = release |
|---|---|---|---|---|
| i biased accumulator overflow (zmm) | yes | **panic** | exact | exact |
| ii `128·colsum` overflow (zmm) | yes | **panic** | exact | exact |
| iii K-tail after overflow (k % 4 = 3) | yes | **panic** | exact | exact |
| iv AMX tier, biased overflow | yes | **panic** | exact | exact |
| v true result out of range | **no** | panic | value mod 2^32 | value mod 2^32, **no panic** |
| control in range | yes | exact | exact | exact |

**The proposed diff (`int8-semantics-v1/accum_wrapping65.diff`).** Five lines, never applied to ndarray:
`wrapping_add` / `wrapping_sub` / `wrapping_mul` at:
- `amx_matmul.rs:995` (scalar tier);
- `amx_matmul.rs:1023` and `:1028` (bias correction);
- `int8_tile_gemm.rs:213` and `:305` (VNNI K-tails).

Single products are untouched: |product| ≤ 255·128 cannot overflow.

On the proposed tree:
- `tailsweep` output is byte-identical to `tailsweep64.json`;
- `cargo test -p ndarray --lib -- hpc::amx_matmul hpc::int8_tile_gemm` gives 23 passed, 1 ignored.
- The scalar-tier line was **NOT RUN**: tier selection always picks VNNI on this host.

**Recommendation, separate from O1.** Apply the diff together with a stated precondition and a test that
pins case v.

The trade-off must be named. Today's debug panic is the only, accidental, signal of a genuinely
out-of-range result. After the change debug matches release and gives a silent modular value there.

If an out-of-range signal is wanted, it has to be explicit, never an arithmetic accident:
- a `checked_matmul_i8_to_i32` that accumulates in i64;
- or a debug-only i64 re-check, which doubles debug cost.

`fallback_path` in `int8_tile_gemm.rs:321` is a separate u8×i8 API with its own result contract and is out
of scope.

### O3. Source compatibility: the prepared-softmax reciprocal gate (P1)

**Two stages, with different inputs.**

**Source-global certificate** (`softcert65 global` → `softcert65_global.txt`, **5.41 s, once**). It depends only on:
- the reciprocal algorithm (`GetReciprocal`, `common.h:968-982`, and `one_over_one_plus_x_for_x_in_0_1`,
  `fixedpoint.h:832-853`);
- x_integer_digits = 12;
- int32 arithmetic;
- the supported sum domain [2^19, 2^28) (6.4 N11).

It does **not** depend on any calibration, because the reciprocal is a function of S alone.

Contents, measured on every S in the domain:
- each S's band h = clz(S) ∈ 4..12, with exponent 35 − h;
- the exact reference round(2^62 / (S ≪ h)) is non-increasing within each band;
- both reciprocals are positive;
- **E_h = 6 for every h = 4..12.**

The certificate records the source revision (`5f64e4ad`) and a SHA-256 over `common.h`, `fixedpoint.h` and
`reference/softmax.h` (`0566576b…`). The gate refuses on any mismatch.

**What E_h does and does not cover.** It is specific to this reciprocal algorithm and build. It is not a
TFLite mathematical guarantee. Reuse it only under a matching revision and digest. A different reciprocal,
x_integer_digits, accumulator type or domain needs a new certificate.

**Per-calibration gate** (`softcert65 gate`). Inputs:
- the certificate;
- one calibration's prepared source weights (trace63 `softexp`: admitted flag, A = exp, B = Rescale<12>).

Steps:
1. The calibration's own assumptions are checked: the maximum is admitted, B[0] = 2^19 (the domain's lower
   bound), and every admitted weight is in range.
2. The boundary-pruned search runs with window E_h.
3. Exact reachability (residue rule mod B[0]) runs on the candidates, building and re-checking a witness
   row for each reachable pair.

Decision:
- `PROVED_OUTPUT_EQUIVALENT` when no reachable pair changes a byte;
- `REQUIRES_SOURCE_RECIPROCAL` when at least one does;
- `REFUSE_UNKNOWN` when any assumption, identity or bound fails.

The decision is made at preparation time. Nothing enters the hot loop.

**Independent validation (`softcert65.py`).** It does not use the gate's code. Per calibration:
- **Table:** recomputed from the claimed calibration; its digest must match.
- **Candidates:** the set must equal the exhaustive superset reference.
- **Witnesses:** each row needs positive counts of admitted codes and must contain the maximum; its
  recomputed sum must be S. The 6.3 Python recipe must give the claimed source byte, and with the exact
  reciprocal the claimed alternative byte. The TFLM kernel must give the source byte.
- **Unreachable claims:** a negative remainder is recomputed; a gap claim is re-checked by an unbounded-coin
  DP on Python integers.
- **Equivalence:** for a PROVED decision, 300 random admitted rows must agree between the kernel, the source
  recipe and the exact recipe.

**14 known calibrations (reconciled with 6.4 N12): TESTED, all valid.**
- 601 candidates, 529 reachable witnesses (all 529 confirmed by recipe and kernel), 72 proved unreachable
  (all re-proved), 0 unknown.
- Calibration 9: `PROVED_OUTPUT_EQUIVALENT`, 0 candidates, 300/300 random rows identical.
- The other 13: `REQUIRES_SOURCE_RECIPROCAL`.

**Held-out calibrations: TESTED, all valid.** Eight new triples (`heldout65.py`):
- scale ∈ {0.03, 0.2, 1/128, 0.125, 0.07, 0.25, 0.0019, 0.04};
- β ∈ {0.5, 1, 1.5, 2, 3}, including three betas the corpus never used.

Each was checked against its own exhaustive superset reference (`recipall65_heldout.json`, 647.7 s on 3
cores). All 8 give `REQUIRES_SOURCE_RECIPROCAL`: 514 candidates, 446 reachable witnesses (each confirmed
by recipe and kernel), 68 proved unreachable.

**Finding: the calibration identity the gate needs is the prepared table, not (scale, zp, β).**
- Two held-out calibrations turned out to have **the same weight table as a known one**:
  - (0.2, β 1) = known 3 (0.1, β 2);
  - (1/128, β 1) = known 11 (1/256, β 2).
- TFLM's softmax prepare uses only β·scale, and softmax works on differences, so the input zero point
  never enters. Only **six** held-out calibrations are genuinely new.
- The same effect shows in the `wrong_calibration` mutation: substituting calibration 2's table for
  calibration 1 (both β·scale = 0.1) changes nothing.
- **Consequence:** the decision must be keyed on the table digest. That catches every real substitution
  (13/14) and correctly treats the 14th as no substitution at all.

**Soundness review of the pruning, verified against the source:**
1. **Threshold inequality.** For admitted w > 0 and sh > 0, SRDHM gives x = ⌊(sh·w + 2^30) / 2^31⌋.
   Then x ≥ β_m ⇔ sh ≥ T_m = ⌈(β_m·2^31 − 2^30) / w⌉, with β_m = m·2^ex + 2^(ex−1). The ceiling is the
   correct direction: the smallest sh reaching the step.
2. **Rounding direction.** All values are non-negative, so `RoundingDivideByPOT` rounds half up and
   unsat ≥ m+1 ⇔ x ≥ β_m. A weight of 0 gives −128 under both arms and is skipped.
3. **Endpoints.** A byte differs ⇔ some T_m ∈ (min(sh_s, sh_x), max(sh_s, sh_x)], so |sh_x − T_m| ≤ E_h.
   The window [T_m − E_h, T_m + E_h] is closed on both sides, and the binary searches take the first S with
   sh_x ≤ T + E and the last with sh_x ≥ T − E.
4. **Saturation.** Only steps m = 0..254 are visible; unsat ≥ 255 clamps to 127, and unsat ≥ 0 since x ≥ 0.
   `T > INT32_MAX` thresholds are skipped, because no reciprocal reaches them.
5. **Monotonicity and bound.** Both are certified on every S. A band transition is handled per band with
   that band's exponent; each S belongs to exactly one band.
6. **Weights.** Every distinct admitted A is enumerated.
7. **Reachability.** Exact (6.4 N12), cross-checked.
8. **Domain.** Only the supported [2^19, 2^28) is searched.
9. **Arithmetic.** Thresholds are __int128. Reachability additions use `__builtin_add_overflow`. Row sums
   are __int128, refused on mismatch.

**Mutation controls (`softcert65_run.json`, 14 known calibrations each).**

"Affected" counts calibrations whose result changed; the rest are unchanged ("valid"). Calibration 9 has
no candidates, so mutations of the search cannot change it.

| mutation | affected | caught as |
|---|---|---|
| E_h − 1 | **0/14** | **ineffective**: one unit of slack (6.4: window 5 already complete) |
| E_h − 2 | 2/14 | candidate set differs |
| one-sided window [T, T+E] (reversed inequality) | 12/14 | candidate set differs |
| excluded lower endpoint | **0/14** | **ineffective**: absorbed by the same slack |
| wrong exponent band | 13/14 | candidate set and decision |
| wrong weight in threshold | 4/14 | candidate set differs |
| missing mandatory row maximum | 8/14 | witness invalid (+ unreachable claim) |
| omitted reachability check | 13/14 | witness without a row |
| negative multiplicities allowed | 2/14 (the calibrations with gap cases) | typed refusal `witness_negative_multiplicity` / witness invalid |
| witness sum ≠ S | 13/14 | typed refusal `witness_sum_mismatch` |
| wrong source revision | 14/14 | typed refusal `source_revision_mismatch` |
| wrong source digest | 14/14 | typed refusal `source_digest_mismatch` |
| wrong calibration table | 13/14 | table digest (+ candidate set / witness / decision) |

Every mutation that changes anything on the corpus is detected or refused. The two ineffective ones are
recorded as such, never counted as controls.

### O5. Preparation economics (P3)

Measured on a Xeon @ 2.10 GHz with 4 cores, single thread.

**Preparation, decomposed:**

| step | cost |
|---|---|
| source-global certificate (all 2^28 − 2^19 S) | **5.41 s, once per source revision** |
| certificate load and check (reuse) | 0.04 ms median |
| weight-table generation (trace63, incl. process start) | 1.6 ms median |
| table parse and check | 0.08 ms |
| threshold construction + pruned evaluation | 8.3 ms median (0.56–46 ms) |
| reachability graph (Dijkstra mod 2^19; skipped with no candidates) | 270 ms median (0.003–437 ms) |
| witness construction | 0.05 ms |
| **gate total, marginal per calibration** | **284 ms median; calibration 9: 2.6 ms** |
| replay cold load: manifest integrity | 0.75 ms |
| replay cold load: table digests | 0.9 ms |
| replay fixtures (dominated by the independent DP on unreachable cases) | ≈ 115 ms |

The 6.4 figure of 7.2 s is now decomposed:
- 5.4 s is the source-global bound, which is reusable;
- the marginal per-calibration cost is 2.6–479 ms, dominated by reachability, which runs only when
  candidates exist.

**Execution** (`perf65.txt`, `perf65_runs23.txt`; three runs; parity beside every arm). All
source-recipe arms show 0 mismatches against the kernel.

- **Reciprocal alone, per row:** source **27.6–32.5 ns**, exact **3.5 ns**. Saving ≈ **26 ns per row**, stable
  across runs, calibrations and n.
- **Complete recipe, source − exact, per row:**
  - n ≤ 64: 15–37 ns, consistent with the isolated saving;
  - n ≥ 256: within run-to-run noise (−279 to +1,416 ns per row on a 1–7 µs row).

  The saving is real but too small to resolve against whole-row cost at large n.
- **Parity:**
  - the exact arm is admitted only on calibration 9, with 0 mismatches in every run;
  - on calibration 10 (not admitted), random rows already give **1 mismatch at n = 8 in all three runs**.
    This is an observed divergence on ordinary data, consistent with the gate's decision.
- **Kernel vs prepared source recipe** (6.3's result, re-measured): kernel 152–37,110 ns per row against
  recipe 68–7,809 ns per row. The prepared source recipe is the large gain, and it needs no reciprocal
  substitution at all.

**Amortisation, computed only where the saving is positive** (calibration 9, Δ ≈ 26 ns per row):

| reuse model | rows | saving | marginal gate (2.6 ms) paid back? | + global certificate (5.41 s) paid back? |
|---|---|---|---|---|
| one-shot, 1 row | 1 | 26 ns | no | no |
| 100 executions × 64 rows | 6,400 | 0.17 ms | no | no |
| 10,000 × 64 | 640,000 | 16.6 ms | **yes** | no |
| 1,000,000 × 64 | 6.4·10^7 | 1.66 s | yes | no (unless the certificate is shared) |
| long-lived inference | ≥ 2.1·10^8 | ≥ 5.4 s | yes | **yes** |
| cached compilation (decision stored with the recipe identity) | any | per row | 0 after first | 0 after first |

- **Break-even:** N = ⌈ΔT_prepare / Δ⌉ ≈ **98,000 rows** for the marginal gate, and ≈ **2.1·10^8 rows**
  if the global certificate is charged to this one calibration.
- The certificate is reusable across every calibration and model on the same source revision, so in
  practice it is charged once.
- **For the 13 REQUIRES calibrations the runtime saving is zero.** Their 0.1–0.48 s gate buys evidence
  (the witness list and a refusal to substitute), not speed.

**Policy, unchanged and now measured.** Decide at preparation, store the decision with the recipe
identity, and execute the chosen method directly.

Sparse per-row reciprocal exceptions are **not recommended**:
- a per-row membership test over the witnessed S values would cost about as much as the 26 ns it saves;
- and it would add a branch to the hot loop.

Not pursued (NOT RUN).
