1. rosetta/build_alignment.py -- normalize_en "-es" branch, silent-e bug
=====================================================================
BEFORE: stem_no_es = t[:-2]; treated as sibilant-cluster (return stem_no_es,
i.e. drop BOTH the 's' and the silent 'e') whenever stem_no_es ended in
"s"/"x"/"z" OR "ch"/"sh". This is wrong for any silent-e word whose
consonant before the 'e' happens to be a bare 's' or 'z': "house" (unchanged,
doesn't end in -es) vs "houses" (-> "hous", WRONG) never merged. Same defect
for prize/prizes ("priz" != "prize").

AFTER: only "ch"/"sh"/"x" endings, or a DOUBLED final consonant (ss/zz,
covers witness/witnesses, kiss/kisses), are treated as the unambiguous
sibilant-insertion case. A bare single terminal 's' or 'z' now falls through
to the plain "strip final s, keep e" branch (this is the Bible-corpus-
appropriate default: house/prize/praise/purpose/curse-class words vastly
outnumber genuine no-silent-e sibilant nouns like bus/quiz in the KJV).

VERIFIED (ran normalize_en directly, no data files needed):
  house/houses   -> house/house   MERGE (was house/hous, split -- FIXED)
  prize/prizes   -> prize/prize   MERGE (was priz/prize, split -- FIXED)
  praise/praises -> praise/praise MERGE (bonus, same class)
  purpose/purposes -> purpose/purpose MERGE (bonus, same class)
  box/boxes      -> box/boxe      still a MISMATCH -- but this is a
                     PRE-EXISTING, UNRELATED limitation: "boxes" is 5
                     chars, the "-es" branch's own len(t)-2>=EN_MIN_STEM_LEN
                     (4) gate excludes it (5-2=3<4) BOTH before and after my
                     change, so it falls through to the plain "-s" branch
                     regardless of my fix. Not touched, not in scope, and
                     "box"/"boxes" do not occur in the KJV corpus this
                     script processes, so it is inert in practice.
  witness/witnesses, kiss/kisses, dish/dishes, church/churches, grape/grapes
                 -> all still correctly merge (regression-free).

2. rosetta/build_rosetta_probe.py -- dead per-anchor verse-dump cap
=====================================================================
BEFORE: `if name == "swallow" or len(receipts) < 400:` -- `receipts` is the
OUTER list (one entry appended per ANCHOR NAME, once, after the inner loop
finishes), so during the entire "swallow" anchor's pass len(receipts)==0,
and during "grape"'s pass len(receipts)==1. The condition is TRUE for every

small structural harness (no data files needed): built the exact list-state
sequence the real loop produces and showed len(receipts)<400 is invariant
True regardless of the verse index.

FIX: switched to `for idx, k in enumerate(sorted(hits)):` and
`if name == "swallow" or idx < 400:` -- idx is the correct per-anchor verse
counter the cap was meant to bound.

COULD NOT RUN END-TO-END: build_rosetta_probe.py needs all 4 lanes (kjv,
luther1545, elberfelder1905, bkr); only 3 are present in this environment
(kjv, luther1545, tischendorf -- no elberfelder1905.json, no bible_bkr.json,
and I am not permitted to fetch over the network). The `grape`/`swallow`
anchors in this script only have ~1-50 KJV hits each historically (per the
committed reports elsewhere in this session's artifacts), so the cap was
likely never VISIBLE as a size difference in practice even before the fix
-- it is a real bug (the code never did what the comment says), but the
practical report-size impact on the anchors actually configured here is
probably small. If any DOWNSTREAM anchor were ever added with >400 hits,
the report would have silently ballooned; that risk is now closed. No
published number changes as a result of this fix (the cap affects report
verbosity/length, not any computed statistic).

7. wordnet/build_wordnet_rail.py -- per-POS error-rate denominator mismatch
=====================================================================
BEFORE: `by_pos_total[pos]` incremented for EVERY v1 row including ABSENT
ones (before the `if status == "ABSENT": continue`), while `by_pos_wrong`
only increments for non-absent rows. Per-pos table computed
`rate = wrong / by_pos_total[pos]` -- denominator includes absent rows,
numerator does not, so the per-pos rate is systematically UNDERSTATED
whenever a pos has any absent rows. The headline number (`comparable =
total - absent`, `error_rate = wrong/comparable`) does NOT have this bug.

FIX: added `by_pos_absent` counter; per-pos table now reports
`comparable = total - absent` and `rate = wrong/comparable`, matching the
headline definition exactly. Table gained explicit `absent`/`comparable`
columns instead of hiding the distinction.

RAN THE SCRIPT FOR REAL against the actual WNDB data present in this
environment at /tmp/wn/dict (WNDB_DIR=/tmp/wn/dict, full audit, no
--sample): the fixed table reproduces IDENTICAL numbers to the previously
committed report --

    | pos | total  | absent | comparable | wrong | error rate |
    | n   | 117952 |   0    |   117952   | 16901 |   14.33%   |
    | v   | 11107  |   0    |   11107    | 3759  |   33.84%   |

This is because `absent == 0` for BOTH pos on the full committed v1 TSV
(129059/129059 rows are present in WNDB) -- when absent=0, comparable==total
by definition, so old and new formulas coincide numerically. CONCLUSION:
**the previously-published "12.76% overall, 33.84% on verbs" figures are
CONFIRMED CORRECT on the full dataset, verified by an actual rerun, not
assumed.** The bug is nonetheless real and was independently confirmed
with a synthetic counter-example (100 v-rows, 20 absent, 40 wrong: old
formula gives 40.00%, correct formula gives 50.00% -- an 10-point
understatement) -- it would corrupt the per-pos rate on any subset run
(--sample) or any future WNDB/TSV pairing with nonzero absent rows, e.g. a
different WordNet edition or a partial audit. Fixed defensively even
though it happens not to have corrupted the one number that shipped.

9. wordnet/tier_delta.py -- asymmetric absence check (TsvHypernymGraph.tier_delta)
=====================================================================
BEFORE: `tier_delta(self, word_a, pos_a, word_b, pos_b)` checked ONLY
word_a for absence (`if (word_a,pos_a) not in self.hypernym_of and

`ancestors_with_depth` unconditionally seeds `depths = {(word,pos): 0}`

a trivial one-node depths dict, and the call fell through to
NO_COMMON_ANCESTOR instead of ABSENT.

NOTE: I checked the WNDB-path sibling function `tier_delta_between_lemmas`
too (task's phrasing was generic about "ancestors_with_depth") -- that one
is NOT buggy; it already does `if not senses_a or not senses_b: return
ABSENT` symmetrically. The asymmetry is specifically in the TSV-only
fallback class `TsvHypernymGraph.tier_delta`, which is the path this
script uses when no WNDB dict is available.

FIX: added `_is_present(word, pos)` helper; `tier_delta` now checks BOTH
sides and returns ABSENT (listing every missing side) if either is absent.

VERIFIED with a direct falsifier (garbage token "zzzznotarealword" that
cannot exist in the TSV):
  dog/n vs zzzznotarealword/n  -> ABSENT  (was: NO_COMMON_ANCESTOR, WRONG)
  zzzznotarealword/n vs dog/n  -> ABSENT  (word_a side, unaffected by the

I additionally reproduced the OLD buggy function inline and re-ran the

captured above. Also ran the full tier_delta.py against the real WNDB data

by this fix) still produces the same scored table as before (dog/wolf
