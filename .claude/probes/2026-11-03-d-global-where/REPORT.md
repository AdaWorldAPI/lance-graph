## 1. Routing contract: what exists

| concern | mechanism | where | class |
|---|---|---|---|
| global → local, local → global | `LocalMap::local` (counted binary search) / `LocalMap::global` (pointer-table read) | `dt64/src/dr.rs:604-616` | PRODUCTION |
| a bijection within one tile | `LocalMap::prepare` refuses `Duplicate` and `TooMany` | `dr.rs:567-587` | PRODUCTION |
| identity across tiles | `MapTable::locate(frame, tiles, g)` reads EVERY listed tile and refuses an id held twice (`Ambiguous`) | `dr.rs:950-975` | PRODUCTION |
| tile width from the survivor count | `Axis::for_survivors` (DR64 up to 64, DR256 up to 256, then ⌈n/256⌉ DR256) | `dr.rs:63-69` | PRODUCTION |
| version and frame | `MapTable::map(frame)` replays the layout the frame was sealed under; foreign frame → `Stale(ForeignFrame)`; `map_at` future → `FutureVersion` | `dr.rs:909-930` | PRODUCTION |
| frame currency | `FrameStore::check` names the first revision that moved | `dr.rs:442-462` | PRODUCTION |
| relation presence, one shared map | `xlog::Cube` (`new`, `new_tiled`, `add_edge`/`retire_edge` through a `DeltaLog`) | `xlog/src/cube.rs` | PRODUCTION crate, lab callers |
| Scope / Focus | `Scope { id }`: "Policy, checked as its own guard; never part of frame identity"; `Focus { revision }` | `dr.rs:493-505` | PRODUCTION |
| WHERE → one frame, admission | `where_dr3::project` / `LocalSelection::admit` | `dr-math-binding-probe/src/where_dr3.rs:176, 225` | LAB |
| RelationshipMap / MapPalette / ThoughtMapPaletteBinding | no Rust type with these names (`lance-graph/src/config.rs::RelationshipMapping` is the unrelated Cypher config) | plans D-RMAP-1A | PROPOSED |

**Answer to the operator's model:** DR already owns exact, bidirectional, versioned routing, and the cross-selection join needs nothing beyond it.
- Two selections that hold the same global Y at different local positions are reconciled through the global id: `global()` on one side, then `local()` or `locate` on the other.
- Comparing local indices directly is wrong. F4 measures it: 32 by local coincidence against an oracle of 14.

**F13 settles the operator's coupling question.**
- `LocalSelection` couples two concerns: its projected bits depend only on (map, WHERE mask, frame) (13b), yet `admit` also compares the full `MethodSignature` (13a).
- The authorization guard is separate, and the method check is not needed to enforce it: Scope refuses on its own (13c).
- So `SchemaChanged` on a second method over the same axis is an unnecessary coupling for correctness. Whether two MethodRefs may share one selection stays an authorization decision, which Scope already expresses.
- **Caveat:** this is the lab `LocalSelection`; production has no selection type at all (§1).

## 3. DuckDB parity gate

**Gate:** parity or better on clearly identified workloads with exact semantic equivalence; every losing workload is recorded with its cause.
- Answers: 336/336 agree.
- DuckDB runs with its normal optimizer at threads 1 and 4, PREPARE/EXECUTE, 201 warm runs. The Python call floor (median 179 µs, `PREPARE f AS SELECT 1`) is subtracted.
- Ours is single-threaded; "warm" includes the WHERE evaluation and the fold.

### 3.1 What the warm numbers do and do not show

**DuckDB's fixed cost per query dominates every warm comparison at these sizes.** Measured on the same connection (wall, Python included):
- `SELECT 1`: 93 µs
- `count(*) FROM nodes` (65,536 rows): 297 µs
- `count(*) … WHERE a<50` over 65,536 rows: 703 µs
- the same over 10,000,000 rows: 12,106 µs

That is roughly 600 µs fixed per query and about 1.2 ns per filtered row. Our W1 (Quack `Count` over the same 65,536-row lane) is 5.7–10.2 µs, about 0.15 ns/row.

So most warm "wins" (W1, W2, W5a, W7, W7i, W8 on every dataset; most workloads on DR64/DR256) are DuckDB's per-query overhead against an in-process fold. **They are not evidence of algorithmic superiority, and are not claimed as such.** The domain here is at most 4,096 nodes; nothing was measured at the scale where DuckDB's per-row throughput dominates. At 10M rows, our side was not measured (PROBE).

### 3.4 Plan choice by measured cost

- **W3 (EXISTS 2-hop):** `csr` (indexed DFS with early exit) is fastest on every dataset (0.3 – 10.6 µs). `back` (selection-first backward mask) and `tile` (per-x 2-hop row) are 2 – 60× slower.
- **W4 (3-hop distinct):** `csr` wins on DR64/DR256 and `multi_sparse`. Selection-first frontier masks (`front`) win on `multi_medium`/`multi_dense`/`multi_skewed` (110/131/89 µs against csr 2–14× slower).
- So the operator's three plans each win somewhere, and the choice must be made by measured cost.
  - The crossover is fan-out × frontier width.
  - Tile-first (`tile`) never won here.

### 3.5 Allocation and memory

- `alloc_query` is 0 bytes for every warm arm (`ours.json`).
- The presence plane costs n²/8 bytes: 2 MiB for 4,096 nodes, built at cold time.
- Peak bytes per dataset are in `ours.json`; DuckDB `duckdb_memory()` totals are in `duckdb.json` `mem_bytes`.

## 4. Verdict

**ALREADY WORKS**
- Production DR provides exact, bidirectional, versioned, multi-tile routing: `LocalMap`, `MapTable::{map, map_at, locate}`, `Frame`/`FrameStore`, `Axis::for_survivors`.
- A cross-selection reference resolves through the global id with no copied object, no new relation table and no new identity store. Measured: F1–F5, F10, F11, F18.
- Presence change through the relation plane works: F6, F7.
- XOR consistency checking works: F8, F9.
- Quack WHERE → Keep is exact (F0).
- Folds allocate nothing (F14, F15).

**WIRE NOW** (lab-proven, small)
- Route a selection into the relation frame ONCE per frame and reuse it.
- Every multi-tile loss above is per-id `locate`, never the fold. Routing once is what `reuse` (5 µs vs 650–970 µs) and the Cube's "each id looked up once at construction" already do.

**OWNER DECISION**
- (a) The coupling in `LocalSelection::admit` (`where_dr3.rs:244`): F13 shows the projection is method-independent and Scope already refuses separately. May one admitted selection serve several MethodRefs under one Scope? (EXO-46)
- (b) Whether a global → tile index (one lookup instead of reading every listed tile) is wanted beside `locate`'s ambiguity scan.
  - `locate`'s O(tiles) read is deliberate: it refuses an id held twice.
  - The cost it puts on multi-tile cold paths is measured above.
- (c) No production type yet holds a relation presence plane whose two axes come from one frame, outside `Cube` internals.

**PROBE**
- Throughput at a scale where DuckDB's per-row cost dominates (≥10M rows, wider domains). This is the gate that remains unanswered.
- DR256 multi-tile plane build via `Cube::new_tiled` instead of the probe's own `Plane`.

**PARK**
- General recursion (EXO-73), non-Boolean Bag expansion beyond the W6 degree product (EXO-108), physical disk prefetch, unrelated runtime work.

**SKIP**
- Duplicate witnesses, per-object allocation, a second routing store, mask transfers across programs, new Gather operators, complete executor migration.
